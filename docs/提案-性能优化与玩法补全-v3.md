## A 包 · 性能优化

原则：**先测量、定预算，再动手**；不凭感觉优化。每一项都要有改前/改后数字。地图扩容（B6.4）后本包权重上升：街区懒加载从"优化项"变为"必需项"。

### A1 测量与预算（第一步，任何优化之前）
- 定点采样场景：广场看钟楼、纪念馆前庭、冰湖看灯塔、酒馆室内，四处固定机位（地图扩容后按新区位重订）。
- 记录：FPS（均值 + 1% low）、帧时间、draw calls、三角形数、JS 堆、首屏可玩时间。工具：浏览器 Performance 面板 + renderer.info，PC 与手机各一轮。
- 目标设备底线（**已定版**）：中端安卓（骁龙 7 系）+ 近五年 iPhone + 普通核显 PC。
- 预算表（**已定版**）：中端手机全镇漫游 ≥ 30 FPS、PC ≥ 60 FPS；draw calls ≤ 300；可见三角形 ≤ 150 万；首屏可玩 ≤ 5 s（4G）。

### A2 已知嫌疑（按可能性排序，待 A1 数据证实/证伪）
1. 地标建筑逐构件建网格：114 处直接 Mesh + 大量 Group 嵌套，draw call 与场景图遍历成本高。
2. 22 个动态光源：Lambert 材质逐片元算光，光源数直接放大片元成本；雪夜场景多数光其实是静态的。
3. 降雪粒子（snowfall.ts）与全镇一次性加载：无分块/流式，远处建筑与近处同价渲染，无距离剔除。
4. 体素酒馆路径 1,189 KB 独立包：与 blockout 并存期间的加载与内存双份成本，迁移合并时要处理。
5. 碰撞/行走几何与渲染几何同精度：碰撞查询在主线程逐帧跑，几何越细越贵。

### A3 手段清单（A1 数据出来后按收益排期）
- 静态几何按材质合并（BufferGeometryUtils.mergeGeometries），地标建筑从"每构件一个 Mesh"改到"每材质一个 Mesh"。
- 重复构件全面 InstancedMesh 化：灯具、栏杆、窗框、摊位、树木（森林已做，推广到街道与广场）。
- 光源预算：静态光改烘焙/顶点色或假发光材质（MeshBasicMaterial 已有先例），动态点光源压到个位数；引入画质分档时按档增减。
- 距离剔除与 LOD：按街区设可见距离，远处建筑换低模/关闭内饰渲染；相机视锥外不渲染内饰。
- 降雪改 GPU 粒子 + 按档位调密度，低端机可关。
- 代码分包：按街区/建筑懒加载，首屏只下广场周边；townBlockout 与酒馆路径合并时统一处理。**地图扩容后此项为必需。**
- 碰撞几何单独低模化（已部分如此：注册的 floors/colliders 是盒子），渲染精细化不回灌碰撞。

### A4 画质分档（已定版：流畅优先）
- 高/中/低三档 + 按帧率自动降档；光影按 PLAN 既定"根据访问设备性能分档"执行。
- **默认策略已定版**：默认档以 A1 目标设备实测的流畅档为准，帧率跌破阈值自动降档——先保流畅，再谈画面。任何档位下不允许出现持续卡顿。

### A5 验收
- 四个定点场景 × 三台设备（中端安卓、iPhone、核显 PC）的 FPS 与帧时间表，附改前对比。
- 多人压测在联机包完成后补：N 个化身同屏的帧率与同步开销单列。

## B 包 · 玩法补全

设计原则（从 PLAN §4 既定内容长出来，不另起炉灶）：
1. **共同完成**：核心乐趣是"大家一起把一件事做成"，不是单人打卡。
2. **留痕持久**：祝福、信件、点亮成果要存下来、再来能看到（PLAN 已定：愿望与公共成果需持久化）。
3. **低门槛参与**：点链接进来的人 30 秒内能参与第一件事。
4. **回访理由**：收集进程与未完成的共同目标，而不是一次性参观。
5. **地标必有真交互**（Thomas 19:24）：核心地标不能只是能走进去看——窗能开关、门能进出、凳子能坐下是已有的样子，每个核心地标至少要有一件真正能动手做的事。钟楼目前**零交互**，是点名要补的头号对象。
6. **镇上要有"人"**（v3 新增）：NPC 居民让镇子活起来，且他们是朋友们了解托马斯的窗口（B6.1）。

### B6 大功能与世界扩展（v3 新增，Thomas 第二轮反馈）

#### B6.1 NPC 居民 · 专答"关于托马斯"（已定方向）
- 镇上入住 5–8 位 NPC 居民，有常驻地点与作息路线（沿街区走动），让镇子有"人气"。
- **NPC 不讲纪念馆、不当导游**：他们只回答关于托马斯本人的问题——怎么认识他的、和他关系怎么样、他的日常与喜好，以及**只有亲密的人才知道的问题**。朋友进来能在镇上"打听托马斯"，这正是这个镇子区别于任何游戏的私人性。
- 问题库分四档：A 相识 / B 关系 / C 日常与喜好 / D 只有亲密的人才知道。框架与问题清单见配套文件《NPC问答-问题库框架》。**答案只能由 Thomas 本人提供**（含每位 NPC 与他的关系设定），Muse 只搭框架，绝不编造；D 档上线前由 Thomas 逐条过目。
- 玩法形态：闲聊模式（按 E 选问题问）+ 可选的考验模式（"你有多了解托马斯"答题判分，与 PLAN 既有的"昵称关系问答"落地合流，成绩可进戳册）。边界沿用 PLAN：允许跳过和不再提示，答案按游戏昵称口径提供。
