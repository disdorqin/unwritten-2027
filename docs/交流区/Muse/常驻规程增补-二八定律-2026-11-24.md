# 常驻规程增补 · 二八定律（2026-11-24，Thomas 定，项目级原则）

**总则：项目的时间按二八分——约八成投入建模施工与优化打磨，测试验证二成封顶。**

Thomas 2026-11-24 亲定（复述当日批评）：此前大部分时间浪费在反复测试上——看看哪处代码过没过某个测试，是细枝末节；重头应该是干活：把东西建出来、建好，最后看卡不卡、把性能优化好。本条与《游戏快速构建口径》（2026-11-20）同向，是其量化版：那条定「验什么」，本条定「时间怎么分」，两条同时有效。

## 执行口径

1. **八成给建模与优化**：施工（形/饰/互）是主业；优化是专门轮次（精修轮 4「优」）集中做——静态合并、烘焙、减面、光照代价评估都在那一轮，不许挤占施工轮，也不许无限后延。
2. **测试只留三件**（快速构建口径）：构建过／浏览器启动 0 报错／功能第一人称实走一遍。日常批次**不跑全量测试**；全量只在切版前跑一次，基线失败名单照旧对表。
3. **性能只带一个数**：每件交付在回执里带一个关键场景 FPS 实测数即可，不做普查式扫描与逐值对表；卡不卡由这个数＋实走体感判，问题攒到优化轮集中处理。
4. **禁止为测试而测试**：逐值回归、万点扫描、证据卷宗、为覆盖率新增用例、为维护测试而改实现——一律不许。既有测试与新实现冲突时，先判测试是不是在钉旧行为：是，则改测试；不许反过来削实现凑绿。
5. **总控收账同此**：抽查关键项＋定向测试，不全量重跑（切版批除外）。
6. **红线例外（不在降级之列）**：①玩法关键高程的测试钉不许松（2026-11-23 裁定，批88/89 前例）；②切版门的 presence 编译模拟保留（批34 部署卡死前科）；③浏览器启动 0 报错是硬门，任何批次不许豁免。

## 适用

四分支窗、GPT 四窗、朋友线、总控自身，一体适用。各窗回执的门检行从简：写明三件结果与 FPS 一个数即可，不再附全量计数（切版批与总控点名时除外）。
