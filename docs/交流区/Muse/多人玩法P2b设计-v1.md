# 多人玩法 P2b 设计 v1（雪球互掷 / 文字聊天 / 活动姿态）

> 状态：设计稿，待 GPT 施工、Muse 验收。基线：P2a 验收钉死树 `12efc63` 源码实读（2026-11-18）+《多人最小版设计-v1》（下称 P2a 设计稿）+《多人负载与交互流畅方案-v1》（下称负载方案）§3 预留接口 +《屋舍空间与火车烟花物理综合设计-v1》（下称综合设计）主题一/二衔接口径。
> 需求来源：Thomas 2026-11-18——P2a 滚动上线后，他与舍友先用**电脑双人联机**实测；P2b 是紧接着的玩法层。手机端同步推进但不是本稿重点，本稿所有呈现均不破坏触控路径。
> 硬约束（沿 P2a，不再论证）：服务器 2 核 / 2 GB、公网 4 Mbps / 月 300 GB；presence 只做中继、不做模拟；同步失败必须静默降级为单人版；性能参考线 draw calls ≤300、可见三角 ≤1.5M、同步+事件 CPU p95 ≤0.5 ms/帧（负载方案 §2.6），超线以真机体验裁决。

## 0. 现状基线（实读结论，设计的出发点）

P2b 的一切设计必须落在 P2a 的**实装口径**上（第二轮验收裁定：与设计稿偏差处实现为准）：

- **服务端** `src/presence/server.ts`：文本帧只有 JSON `join`/`leave` 两种消息；二进制帧一律按 12 B 状态记录解析。快照 = 1 B 人数 + N×12 B 记录，**按版本变化驱动**逐收件人发送（可见集或任一记录版本未变就不发）。连接级令牌桶限速（突发 2、10/s 回充）；`maxPayload` 512 B；发送背压线 `bufferedAmount > 32 KB` 丢弃。档位（PRESENCE_TIERS）按在线人数选档，兴趣判定 = 32 m 格 + 二维距离（D8 裁定：高度不参与）。
- **状态记录 12 B 已占满**：id u16 / 东 u16 厘米 / 北 u16 厘米 / 高 u16 厘米 / yaw u16（整圈 65536）/ seq u16。**没有 flags/gait 字节**（P2a 设计稿 §4.2 的 flags/gait 在实装中被 seq 取代，D4 裁定实现为准）。→ 推论：P2b 的姿态**不进二进制记录**，走独立通道（§3）。
- **客户端** `town-presence.ts` + `town-presence-motion.ts`：10 Hz 变更才发 + 静止终态包；远端化身保留 8 条样本历史，120 ms 插值延迟 / 250 ms 外推上限；化身渲染 `town-presence-avatars.ts` 为单个 InstancedMesh，**22 部件/人**（`voxelPersonParts`），当前只按 yaw 旋转整身、**部件无摆动**（NPC 渲染器 `town-npc.ts` 的 `pose()` 有 swing 摆动与投掷手势的现成数学，P2b 姿态渲染照此扩展，见 §3.3）；名字牌 DOM 池 48 个、40 m 剔除；实例缓冲已用 `addUpdateRange` 部分更新。
- **雪球单人版** `town-snowball.ts` + `town-snowball-world.ts`：确定性弹道——重力 **g = 12 m/s²**，速度 `12 + 14×power`，控件 v2 后玩家投掷恒为满速 **26 m/s**（蓄力分级已废止）；固定步长 1/60 s 模拟；弹丸池 **64**（`shotLimit`，池满时 `launch()` 已实现**取最旧槽覆写** = drop-oldest 现成）；火花池 72；投掷冷却 **0.25 s**、弹药 10。碰撞 sweep 对手 = 世界几何 + 目标表（本地玩家胶囊 `playerTarget` r=0.27 / h=1.78 / id `local`、NPC 目标、练习靶），命中分 head/torso 区（头部线 = 身高 ×0.78）。命中反馈 `snowball-hit-feedback.ts`：DOM 雪糊屏 + 相机微震（head 不透明度 .76 / 560 ms、torso .46 / 440 ms），纯本地、零 GL。雪仗榜 `town-snowball-board.ts` 已按 thrower id 记行（throws / hits / bestStreak / received），NPC 投掷者已在榜——**远端玩家只需作为新行加入**。本地事件 `onEvent`（throw / impact / miss，含 origin/dir/power）已存在，P2b 的网络层挂在它上面。
- **活动姿态的本地来源**（viewer.ts 实读）：就座 `seated`（含酒馆吧凳，`seated.tavern`）、泡汤 `hotSpringSoak.active()`、滑冰 `skatesOnIce()`、饮酒 `tavernActivity.carryAction()` 的 drink 动作、乘车 `railway.boarding / boardingGround`。姿态同步 = 把这五个既有状态源接到 presence，仅此而已，不新造状态机。
- **前置依赖**：P2a 放行条件中的 D1（自动重连）/ D2（在线数 HUD）是滚动后第一修复批；P2b 的姿态/聊天状态恢复依赖 D1 的重连 + 花名册重放语义（§3.2）。D1/D2 未落地前 P2b 可施工，但联调验收排在其后。

## 1. 雪球互掷同步

### 1.1 权威划分（裁决）

| 环节 | 归属 | 理由 |
|---|---|---|
| 投掷生成（origin/dir/时刻） | **投掷者权威** | 与 P2a「本地零等待」同源：投掷者按下/松手即本地出球，网络不参与手感 |
| 转发 | **服务端哑转发** | 只校验、钳制、按兴趣扇出；不模拟、不判定命中（沿 P2a 中继定位，不引入第二个世界权威） |
| 飞行模拟 | **每客户端本地各算一份** | 弹道是解析确定的（§1.2），不需要服务端模拟 |
| 命中世界/NPC | **各客户端本地结果** | 世界几何全端一致 → 结果一致；NPC 是本地状态 → 命中 NPC 只产生本地迸溅，不计分、不确认 |
| 命中玩家（计分与反馈） | **被击者权威** | 被击者客户端用自己的胶囊（自己屏幕上的真实位置）判定；投掷者端的命中只是「疑似」，等被击者确认才计分（§1.3） |
| 被击反馈（雪糊屏/震屏） | **被击者本地触发** | 反馈模块本来就是纯本地 DOM+相机，与判定同端，零网络往返 |

### 1.2 抛物线与落点一致性：参数同步，不用种子

弹道完全由 `(origin, dir)` 决定：初速是协议常量 **26 m/s**、重力常量 **12 m/s²**、步长 1/60 s、射程/寿命上限沿用单人版（弧长 35 m / 2.6 s）。因此：

- **不传 power、不传 velocity、不传种子**：投掷事件只带 origin 与 dir（§1.4），每端用同一组常量重演。随机种子同步是给含随机散布的系统用的，本弹道无随机量（迸溅火花的伪随机以 shot id 为种子，单人版 `burst(at, target, seed)` 已如此，各端同 id 同图案）。
- **世界命中点一致性**：各端 sweep 的是同一份世界几何（同版本构建），开放地落点分歧只来自浮点末位，验收线 ≤0.5 m（§6）实际预期为厘米级。
- **时刻对齐**：接收端在**收到事件的那一帧**以 t=0 生成弹丸，不做发送时刻回拨。网络单程时延（同城宽带 ~10–40 ms）使各端飞行相位差 ≤40 ms、弹道上位置差 ≤约 1 m——但每端模拟自洽（球从对方手边出、沿正确弹道飞、命中判定在被击端以被击端相位为准），观感与公平性都不受损。投掷臂摆动画由同一事件在接收端触发，与出球同帧，天然同步。可选的精修（发送端时间戳 + 仪式时钟偏移回拨生成）列为观察项，v1 不做。
- **高度门**：生成远端弹丸前先比 origin 高度与本地玩家高度，差 >10 m 直接不生成（综合设计口袋屋在 +150 m：屋内客户端不会被地面雪仗的弹丸渲染打扰，反之亦然；与 D8 的二维兴趣判定互补，事件扇出仍按二维，客户端本地丢弃）。

### 1.3 命中判定与计分流

1. 投掷者端：自己的球走**现有全部逻辑**（弹药、冷却、sweep 世界+NPC+练习靶），并**新增远端玩家胶囊为目标**：把可见集内每个远端化身按其插值位姿登记为动态胶囊目标（r=0.27、h=1.78、id=`p:<会话id>`，每帧更新坐标，机制与 `playerTarget` 每帧回写同法）。球命中远端胶囊 → 本地迸溅 + 榜上该球标记「疑似命中」，**不立即计 hits**。
2. 被击者端：远端球（§1.5 的 `throwRemote`）的 sweep 目标 = 世界几何 + **自己的 `playerTarget`** + NPC/练习靶（后两者只为迸溅观感）。命中自己的胶囊 → 立即 `hitFeedback.hit(zone)`（zone 由同一 0.78 头部线判定）+ 发出 **hit 确认事件**（§1.4）+ 自己榜上给投掷者行 hits+1、自己行 received+1、连击口径沿单人版（投掷者 streak 由其 hits 序列推导，各端同源事件 → 同结果）。
3. 服务端把 hit 确认按兴趣集转发（同 throw 的扇出范围）：投掷者端收到 → 疑似转正，hits+1；围观端收到 → 同步各自榜行。**确认是计分的唯一依据**：投掷者疑似未获确认（对方屏幕上躲开了）不计分，被击者确认而投掷者没看见命中（插值位姿差）照样计分——一句话：**被击者的屏幕说了算**。
4. 确认丢失兜底：确认走 WS/TCP 可靠有序，不存在传输丢失；被击者掉线则该球自然无确认，按未命中处理。无重发、无服务端对账（朋友量级不买此保险）。

### 1.4 协议：二进制事件帧（新帧族，不动状态记录）

P2a 的二进制通道目前只有一种帧（12 B 状态）。P2b 新增**事件帧族**，以首字节 `0xFF` 与快照帧区分（快照首字节 = 人数 ≤48，永不为 0xFF；客户端→服务端方向以帧长 12 = 状态、首字节 0xFF = 事件区分）。全部小端。

**投掷帧 C→S（16 B）/ S→C 转发（18 B，多投掷者 id）**

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u8 = 0xFF | 帧族标记 |
| kind | u8 = 1 | throw |
| ball | u16 | 投掷者内自增序号（回绕；接收端以 (投掷者, ball) 去重，3 s 窗口） |
| （S→C 追加）thrower | u16 | 服务端注入的会话 id |
| origin 东/北/高 | 3×u16 厘米 | 与状态记录同量化；高度为绝对高（脚底+约 1.5 m 的出手点由发送端算好） |
| dir x/y/z | 3×i16 | 单位向量 ×32767（发送端归一化；服务端只验有限性与模长 ∈[0.5, 2]） |

**命中确认帧 C→S / S→C（8 B / 10 B）**：magic、kind=2、ball u16、thrower u16（C→S 由被击者填、S→C 追加 confirmer u16 即被击者 id）、zone u8（0=torso，1=head）。

**帧聚合预留（负载方案 §3 杠杆 3 的接口义务）**：S→C 的一个 WS 消息内**允许**连续排布多个事件帧（接收端必须循环解析至消息末尾）；v1 服务端仍一事件一消息发送，但解析侧先行支持聚合——日后服务端按 tick 聚合时只改发送侧，不动协议。

**校验与滥用防护（服务端，全部沿用 P2a 钳制风格）**：

- origin 合理性：与投掷者最近状态记录的出手点（记录位置 + 高约 1.5 m）距离 ≤3 m，超出丢弃（防隔空刷球；传送后记录即时更新，不误伤「前往」）；
- 投掷令牌桶：每连接独立桶，回充 **4/s**、突发 **6**（合法上限 = 冷却 0.25 s 的 4/s）；超限静默丢弃；持续洪水沿 P2a 既有纪律（消息速率异常 → 断开）；
- 弹药/冷却仍由投掷者客户端自律（单人版逻辑不动），服务端不复核弹药——朋友服口径：服务端只防「协议层刷屏」，不防「玩法层赖皮」；
- 接收端并发上限：同一投掷者在本端活跃的远端弹丸 ≤**8** 颗，超出的 throw 丢弃（防单人刷满公共池，见 §1.5）。

### 1.5 弹丸池与 drop-oldest 口径

- 远端弹丸**进同一个** `createTownSnowballFight` 实例：新增入口 `throwRemote(origin, dir, throwerKey)`（`shotBy: 'remote'`），不扣弹药、不占本地冷却、不计本地分、不清本地连击；其余（固定步模拟、迸溅、寿命）与现有弹丸完全同路。
- 池仍为 **64**：负载方案 L3 极端空中球 ≈77 > 64 的取舍按其推荐定案——**drop-oldest**，且实现现成（`launch()` 池满时覆写最旧活跃槽）。覆写顺序的实际效果：先牺牲最老的远端球/本端 NPC 球，本端玩家自己的球 id 最新、天然最后被覆写——不额外做优先级逻辑，靠 id 序自然成立，验收时验证此性质（§6）。
- 迸溅封顶（负载方案 §3 杠杆 4 的接口义务）：同屏迸溅组数封顶 **8 组**——火花池 72 已有覆写轮转，远端命中在封顶外只出命中点小雪点、不整组迸溅；本地玩家自己球的迸溅不受此限（先到先得按时间序，口径写进施工常量 `REMOTE_BURST_CAP = 8`）。

## 2. 文字聊天

### 2.1 裁决：两个频道都要，共用一个输入框

- **近场频道（默认）**：分发半径 40 m（与铭牌剔除距离一致——看得见名字的人才听得见），头顶气泡 + 聊天记录行双呈现。这是「站在旁边说话」的自然形态，雪仗/同乘/屋内相遇都靠它。
- **全镇频道**：分发给全部在线者，只进聊天记录行（发送者在 40 m 内时同样冒气泡）。理由：小镇 640×512 m，约人靠它——「来广场打雪仗」「火车要开了」是联机活动发生的前提；成本与近场几乎无差（§5），不做等于把联机协调逼回微信。
- UI：面板区一个输入框 + 频道切换钮（近场/全镇，会话内记住选择）；Enter 聚焦/发送，Esc 还焦。桌面优先（Thomas 本轮双人测在电脑），触控端点击输入框走系统键盘，不另做一套。

### 2.2 协议（JSON 文本帧，沿 P2a 文本通道）

- C→S：`{type:'chat', scope:'near'|'town', text}`；S→C：`{type:'chat', id, name, scope, text}`——服务端注入 id/name 后**序列化一次**、同一字符串扇出（负载方案 §3 杠杆 1 的 serialize-once 在文本通道天然成立，`broadcast()` 已是此形态，事件版照抄并按兴趣过滤收件人）。
- 服务端校验：text 须为字符串、去控制字符（复用 `validName` 同款正则口径）、长度 ≤**100 字符**（按码点计；100 CJK 字符 ≈300 B + 信封 <512 B `maxPayload`，不需改上限）；scope 非法值按 'near' 处理。
- 限频：每连接令牌桶 1 条 / 1.5 s、突发 2；超限静默丢弃（不回错、不踢人——聊天手快不是攻击）。
- 近场收件人：以发送者最近记录为圆心、二维 40 m（与兴趣判定同源数据，O(在线数) 遍历即可）；**口袋屋规则**（综合设计 §1.5）：发送者与接收者一内一外时不投递近场（高度差 >10 m 判异界，与 §1.2 高度门同阈值）——屋里说话不漏到东北角野地上空，反之亦然。全镇频道不受此限（全镇广播本就跨界）。

### 2.3 呈现（零 GL 成本）

- **气泡**：DOM 池（每化身至多 1 个活动气泡，复用名字牌 overlay 容器与投影路径——气泡锚在铭牌上方，投影/剔除与铭牌同帧同口径，40 m 外不显示）；新消息替换旧气泡，停留 **4.5 s** 淡出；文本只在到达时写 `textContent`（名字牌同纪律，杜绝注入与每帧 DOM 写）。
- **记录行**：面板聊天区保留最近 6 行（近场/全镇同列，全镇行带「全镇」标记），DOM 文本节点，零 GL。
- 本地回显：自己发的消息直接本地上屏（气泡+记录行），不等服务端绕回（服务端转发排除发送者，与 join 广播同例）。

### 2.4 敏感词与内容口径（最小处理）

朋友间测试服，**不做词库过滤**（P2a 设计稿 §8 已定此调，P2b 沿用）：只做结构层防护——控制字符剥离、长度上限、限频、`textContent` 渲染（无 HTML 注入面）。不留存：服务端不落盘、不记日志正文；客户端记录行只在会话内。若将来链接扩散到朋友圈外，过滤/举报另行立项（P2a §8 开放问题，状态不变）。

## 3. 活动姿态同步

### 3.1 通道裁决：独立 JSON 状态消息，不进 12 B 记录

姿态是**低频粘性状态**（坐下能坐十分钟），不是 10 Hz 量：塞进记录要改双端字节布局与黄金向量、且每快照白带一字节；独立消息只在变化时发一条，是显然更优解。

- C→S：`{type:'pose', pose}`（变化时发；join 被确认后补发一次当前姿态——重连恢复靠它 + §3.2 的花名册重放）；
- S→C：`{type:'pose', id, pose}`，服务端存 `peer.pose` 并按兴趣集转发（收件人 = 当前能看见发送者的人）；
- **新入镇者补齐**：服务端在 join 流程中给新人的逐人 join 消息里附带各人当前 `pose` 字段（老客户端忽略未知字段，向前兼容）；已在线者收到新人 join 后，若自己姿态非 0，由新人客户端在收到其首份快照后向服务端请求——简化口径：新人入镇时服务端额外向新人逐人补发一遍非 0 的 pose 消息（消息量 ≤在线数，一次性，可忽略）。

### 3.2 姿态枚举与本地来源

| pose | 含义 | 本地来源（viewer 既有状态） | 备注 |
|---|---|---|---|
| 0 | 站立/行走/跑/跳 | 默认（其余皆假） | 步态摆动由接收端按速度本地推导（§3.3），不占同步 |
| 1 | 就座 | `seated`（长椅/椅/吧凳，含酒馆） | 温泉的 sit 是 2 不是 1（来源不同） |
| 2 | 泡汤 | `hotSpringSoak.active()` | |
| 3 | 滑冰 | `skatesOnIce()` 且在冰面移动中 | 静止站在冰面 = 0（由来源端判定：滑行速度 >0.5 m/s 才报 3） |
| 4 | 举杯饮酒 | drink 动作触发后 **2.5 s** 内 | 瞬态姿态，超时自动回落到下层姿态（多为 1）；发送端以「有效姿态」计算后只发变化 |
| 5 | 乘车 | `railway.boarding` 成立期间 | 姿态用就座预设（§3.3），位置由车厢采样（P2a 采样口径已含乘车世界坐标） |
| 6 | — | 预留（舞台表演/钓鱼等，P2c 议） | |
| 7–255 | — | 预留 | u8 字段，不再扩位 |

发送端维护「有效姿态」：优先级 4（饮酒瞬态）> 2（泡汤）> 5（乘车）> 1（就座）> 3（滑冰）> 0；任一来源变化时重算，只在有效值变化时发消息。投掷动作**不设姿态值**：接收端收到 throw 事件时给投掷者化身播一次 0.35 s 投掷臂摆（事件驱动动画，与出球同帧，`town-npc.ts` 的 throwGesture 是同一动作的现成先例）。

### 3.3 接收端呈现（化身姿态预设）

`town-presence-avatars.ts` 的矩阵合成从「整身 yaw 旋转」扩展为「按部件摆动/姿态预设」，数学照 `town-npc.ts` `pose()`（step = gait × swing，部件表 `swing` 字段已标好腿/臂）：

- **行走摆动（pose 0/3 的动效层）**：接收端按化身插值速度积分步态相位（相位推进 = 速度 × dt × 步频系数，与 NPC 同口径），腿/臂按 swing 摆动——零同步字节，脚步与位移自动对齐（P2a 设计稿 §4.2 gait 字节的意图由本地推导实现，不占带宽）；
- **就座（1/5）**：整身下沉至座面高（根偏移 −0.45 m，以化身上报高度为准做相对下沉）、双腿部件前摆水平、双臂垂放；
- **泡汤（2）**：整身下沉 −0.55 m（水面藏下半身）、双臂外张搭池沿向；
- **滑冰（3）**：双腿以步态相位交替前后剪、上身前倾约 6°、双臂侧张；
- **举杯（4）**：右臂部件（x>0.32 且 y>0.75 的选择器，与 throwGesture 同）上举至口边，保持至姿态回落。
- **脏标记（负载方案 §3 瓶颈 1 的 P2b 预留义务）**：pose 变化时给该化身打脏——姿态预设切换帧全量重算其 22 部件矩阵一次；静止且姿态未变的化身继续走既有路径。实现上姿态预设是每部件的常量偏移表（5 张小表），合成时查表叠加，不引入每帧分配。

### 3.4 带宽增量核算

姿态消息 ≈60 B/条线上 ≈110 B。L3 口径（48 人、人均 1 次/30 s）聚合 1.6 条/s、扇出 ≈64 条/s → 服务端出口 **<10 KB/s**；双人实测场景可忽略。与负载方案 L3 表「姿态事件 <10 KB/s 可忽略」一致，结论不变。

## 4. 火车同乘与屋内相遇的 P2b 衔接（只定本侧补件）

综合设计已定口径，P2b 不重设计、只补以下四件：

1. **火车**：列车位置 = 共享时钟纯函数（仪式批的服务端时钟通道），**不进 presence、不进 P2b 事件**。P2b 侧唯一补件 = 乘车姿态 pose 5（§3.2）；乘员位姿沿 P2a 采样（车厢世界坐标），同车乘客天然互见。双人验收一条：两人同乘一圈，双方屏幕上对方不脱离车厢（时钟误差 ≤0.5 s → 位置差 ≤5.5 m 的口径沿综合设计 §2.5，最坏是车厢内偏移、不出现人车分离即合格）。
2. **屋内相遇**：presence 协议零补件（口袋坐标原样上报，综合设计 §1.5）。P2b 侧补件三条已分别写进正文：近场聊天的口袋门（§2.2）、远端弹丸的高度门（§1.2）、屋内禁掷沿用单人版门控（`sheltered` 下投掷不触发，远端球也进不来——150 m 高差 + 35 m 射程，物理隔离）。姿态在屋内自动成立（围炉就座 = pose 1，屋友互见）。
3. **烟花平时玩法（综合设计主题三 F2）**：其多人同步走**仪式事件通道**，不走 P2b 事件帧族；但通道的服务端形态应与本稿 §1.4/§2.2 同构（JSON 小消息、serialize-once、兴趣扇出）——哪边先落地，另一边照抄其收件人计算与限流代码，不许长出第二套扇出实现。
4. **深雪/物理类**：纯本地判定（综合设计主题四），与 P2b 零交集，不列补件。

## 5. 性能与带宽总账（承接负载方案 §3 的核算）

## 6. 验收标准（双人实测清单，Muse 执行，两台电脑）

**雪球互掷**
1. A 投掷，B 屏幕上弹丸自 A 手边生成并沿弹道飞行，延迟体感 ≤300 ms；开阔地落点双端分歧 ≤0.5 m（双端录屏比对）。
2. B 直射 A：A 屏幕雪糊屏+震屏按区触发（爆头/躯干各验一次，反馈参数与单人版一致）；A 榜上 B 行 hits+1、A 行 received+1；B 榜上自己 hits 在收到确认后 +1（允许 ≤0.5 s 滞后）。
3. A 打中 B 的「影子」不计分：B 急停变向使 A 端疑似命中、B 端未中——B 无反馈、双端榜均不计分（被击者权威验例）。
4. 墙后命中不成立：B 躲墙后，A 的球在双端都撞墙迸溅，无穿墙确认。
5. 对射 spam：两人 0.25 s 冷却节奏连投 30 s——无弹丸丢失性错乱、无帧时尖刺 >50 ms；第三人（或机器人）把空中球顶过 64 时最旧球先消失（drop-oldest 目视验例）。
6. NPC 混战：广场与 NPC 雪仗同场，远端球打中 NPC 只迸溅不计分；NPC 打中 A 的反馈与单人版一致；A 的球打中远端玩家胶囊的迸溅位置正确。

**聊天**
7. 近场：40 m 内发近场——对方气泡+记录行双到；走出 40 m 再发——对方收不到（记录行也无）。
8. 全镇：两端分处地图两端（>300 m），全镇消息记录行互达；发送者在近场时对方同时见气泡。
9. 口袋门：A 进屋、B 在东北角野地（口袋正下方），近场互发均不达；全镇互达。
10. 限频：连发 5 条，第 3 条起被静默丢弃，对方只见 2 条；100 字符上限与控制字符剥离各验一次。

**姿态**
11. A 依次就座/起立、泡汤、滑冰滑行、酒馆饮酒、乘车一圈：B 端化身姿态逐项对应切换（延迟 ≤1 s），饮酒 2.5 s 后自动回落为就座；滑冰静止站冰面时 B 端见站立。
12. B 中途入镇：A 已就座时 B 进镇，B 首见 A 即为就座姿态（花名册补发验例）；断线重连后姿态恢复（D1 落地后验）。

**衔接与降级**
13. 同乘：两人同车，彼此不脱离车厢（§4.1 口径）；下车后姿态回 0。
14. 屋内：两人在屋内互见就座姿态、近场聊天通；屋内长按雪球不触发（沿单人版门控复验）。
15. 降级：雪仗中杀 presence 容器——双端本地雪仗（打 NPC）无缝继续、无弹窗；容器恢复后（D1 落地后）自动重连，事件通道随连接恢复，不残留幽灵弹丸。

## 7. GPT 施工拆分建议

沿既定分工（GPT 施工、Muse 验收），四批串行可独立交付，顺序按 Thomas 双人实测的价值排：

- **批 E1（服务端事件层）**：二进制事件帧族（throw/hit 解析、校验、令牌桶、兴趣扇出、serialize-once 的字节复用）、pose/chat JSON 转发与存储、**事件字节并入滚动出口统计 + 350 KB/s 带宽降档规则接线**、服务端测试（帧解析黄金向量、钳制、扇出范围、降档触发）。此批无客户端配合可自测（机器人发帧）。
- **批 E2（雪球互掷客户端）**：`throwRemote` 入口与 `shotBy:'remote'`、远端胶囊动态目标、hit 确认流与榜行接入（`p:<id>` 行，label=名字）、事件队列（presence.update 内 ≤0.2 ms 排空）、迸溅封顶常量、高度门、投掷臂摆动画。**E1+E2 完成即可交付 Thomas 双人雪仗实测。**
- **批 E3（聊天）**：输入 UI + 频道切换、气泡池（挂名字牌 overlay）、记录行、服务端已在 E1 就绪的转发接线、限频/口袋门验收项。
- **批 E4（姿态）**：viewer 五个状态源 → 有效姿态计算与发送、服务端 pose 存储/补发（E1 已含转发，此批补 join 附带）、化身姿态预设表 + 步态本地推导 + 脏标记、乘车 pose 5 与屋内姿态验收项。
- 每批全量回归（Node + server 测试）+ 回执报实测数字；E2/E4 批回执须含双浏览器自测记录。D1/D2（重连/HUD）若未先行，E3/E4 的重连类验收项顺延，不阻塞 E1/E2 交付。
