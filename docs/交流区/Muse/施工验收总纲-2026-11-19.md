# 施工验收总纲（2026-11-19，主窗口质量规范）

定位：本纲是全线施工的验收宪法。两 GPT 窗口的每一单交付、分支窗口的每一轮审核、主窗口的每一次发令，皆以本纲为准。验收不是走流程：**打回补做是常态，不必每次通过**；一项工作只有过了本纲五关、且经独立复核，才算做完。

---

## 一、总原则（六条，先于一切清单）

1. **功能走查优先**：新场景、新建筑先验功能，后验数值。每处必须先答得出「玩家在这里做什么」，走查不过，后面的关不必看。
2. **证据是实测值**：自报「通过」「已完成」一律不算数。回执必须带测得的数字与提交号；没有数字的结论视为未交付。
3. **缺口如实登记**：测不了、没测到、条件不具备的，写明缺口即可，不许粉饰、不许用「基本通过」糊过去。gaps 标 gaps，是诚实不是失败。
4. **不编造**：NPC 台词不许编造（问答只种子自已记录的事实）；引用、编号、数值不许凭记忆写（引文核查以原文为准）；缺源只报一次，且必须写明所查路径与提交号。
5. **合线每批跑全套**：任何合线批次，root 测试 + server 测试 + tsc 三件齐跑，缺一不算合线完成。
6. **发布只听主窗口发令**：town-release 只在主窗口明文发令后才推；推送后须逐字读 healthz，返回 `town-preview <完整 SHA>` 才算上线生效，读不到即未生效。

---

## 二、验收五关

### 第一关 · 功能走查

- **过关标准**：交付方按「玩家动线」实际走一遍该功能/场景：入口可达、交互可触发、流程可走完、出口可离开；新场景建筑逐处登记「玩家在这里做什么」，每处至少一件可做的事。
- **走查证据**：回执附走查路径记录（从哪进、做了什么、在哪出），不接受「代码里已实现」代替走查。
- **不过关处置**：整单打回，注明卡在哪一步（进不去/触发不了/走不完/出不来）；修好重走，不许只补代码不重走。

### 第二关 · 证据回执

- **过关标准**：回执齐备本纲第三节体例：首行已读清单、实测值表、提交号、缺口登记。数值类主张（时长、计数、比例、性能）必须给测得值与测法一句话。
- **不过关处置**：回执缺项即视为未交付，退回补齐；数值与复核对不上，按第四节处置。

### 第三关 · 全套回归

- **过关标准**：root 测试全绿、server 测试全绿、tsc 全绿；合线批次在合线后的树上重跑一遍（不许拿合线前的绿灯充数）。
- **红项处置**：任何一红，合线不成立。先分清是本批引入还是存量红：本批引入的当批修；存量红登记在案并注明与本批无关的证据，不许顺手「修好」不相干的东西冒充本批成果。

### 第四关 · 启动冒烟

- **过关标准**：浏览器实际打开页面，城镇能启动、无控制台致命错误、首帧正常渲染。此关源于 D2 HUD 教训：根测试与 tsc 全绿时页面照样坏过（viewer 每帧 DOM 写入引用的元素 id 在 town-blockout.html 里不存在，页面带病上线十几分钟）。
- **专项核查**：凡本批给 viewer.ts 新增或修改了每帧 DOM 写入，必须逐个核对所触元素 id 在 town-blockout.html 中真实存在，核对结果写进回执。
- **不过关处置**：冒烟不过，前面四关的结论全部作废重来；此关无豁免。

### 第五关 · 实测口径

- **过关标准**：涉及性能与容量的验收，只认实测：峰值 draws / tris 按场景实测报数；服务器内存、同步流量、冷启动一类只认仪器读数，不认估算。
- **预算的地位**：性能预算（PC 线 450 draws / 2.2M tris）是**参考线**，不是一票否决线；超线要登记并说明真机体验，真机体验为准；但「超线且不登记」不许。
- **重测纪律**：实测套件重跑、重压测、多 bot 压测一律**先报批**——施工跑在主理人的机器上，烧的是他的 CPU/GPU。未批先跑，成果不认，还要登记违规。
- **工具纪律**：测不准就写测不准。估算值必须标注「估算」，不许与实测值混排。

## 三、回执体例（每一份回执照此写）

1. **首行**：「本轮已读 Muse 新文件：……」逐个列出本轮读过的新文件，一个不漏。
2. **交付物清单**：文件 → 提交号，一一对应；本轮动过什么、没动什么，分开写。
3. **实测值表**：每条主张一行：主张 / 测得值 / 测法。没有测的主张不许进表，进缺口栏。
4. **测试结论**：root ×/×、server ×/×、tsc 绿否、启动冒烟过否，四项分列，不许打包成一句「全绿」。
5. **缺口登记**：未做、没测到、待裁定、待批准的，逐条列明并注明卡点（缺什么、等谁）；缺口不许藏进正文。
6. **状态三分**：涉及推送与传达时，分开报告「已推送 / 已被接走 / 对方未读」三种状态，不许用「已推送」冒充「已传达」。

## 四、按工件类型的验收清单

### 场景类（建筑、地形、室内、陈设）

- [ ] 功能登记：每处答得出「玩家在这里做什么」，且已走查
- [ ] 坐标与边界：落位与规格一致；凡动边界，三条硬缝（theaterHouseRelocations 南界、scenery.ts B2a 绑定的精确边界、town-campfires 的广场等值门）同批参数化并给证据
- [ ] 风格：贴合既有体素造型语言，不合格打回重做
- [ ] 峰值实测：该场景 draws / tris 实测报数，超参考线已登记
- [ ] 门与过渡：门登记数对得上台账；进出过渡走查无卡死
- [ ] 陈设文字：标牌类只许通用短词，无编造的人名、单位名、年份

### 系统类（玩法机制、数值、协议）

- [ ] 规则与定版口径逐条对版（数值、档位、边界条件），对不上处逐条列明
- [ ] 边界情形实测：临界值两侧各测一例（如速度档分界、层数上限）
- [ ] 单人可完成：全部机制单人能过，多人只是更好玩
- [ ] 协议克制：无未报备的新增协议号；确需新增，先报主窗口
- [ ] 多端一致：PC 与移动端（拖拽视角）操作口径都走查过
- [ ] 回归：全套三件绿 + 启动冒烟过

### 叙事类（故事线、残页、NPC、讲古）

- [ ] 内容来源：NPC 问答只出自已记录事实，未记录的走角色内回避，零编造
- [ ] 审级合规：镇长讲古全文、真相层文本已过主窗口审；未审不得落单
- [ ] 层级不越界：当前版本只许传说层+暗示，真相词不提前落地
- [ ] 引文核查：引用编号以原文（PDF）为准，不用二手编号
- [ ] 埋种登记：伏笔、遗址、碑文碎句按正典目录编号入账，不散埋

### 运营类（日历、手册、活动排期）

- [ ] 与既有口径对表：时间、节拍、人数假设与庆典线/首周日历等既有稿一致，冲突处标注待裁
- [ ] 红线复核：不签到、不逼肝、无限时独占奖励
- [ ] 可执行性：每一项写明谁做、何时做、做完的标志，不写空话条目
- [ ] 未确认假设单列：如开井时点一类未拍板假设，显式标注「未确认」，不许当定版排产

## 五、复核与打回

1. **独立复核**：分支窗口当轮审，审的是证据不是态度——回执里的关键数字要抽验复算，自检报告说好话不算证据。
2. **打回的写法**：问题单只写四件：问题、证据、期望修复、验收口径。不写情绪、不扩大范围。
3. **重验**：打回项修好后只验被打回的部分 + 全套回归，不许借重验之名重开全单，也不许不验直接放行。
4. **争议**：交付方认为验收有误，举证到主窗口裁断；裁断前状态记「争议中」，不记「已完成」。

---

## 六、发布门（总装与上线）

1. **总装结论的构成**：合线范围清单（哪些已验批次进了、哪些没进及原因）、全套回归结果（root/server/tsc 数字）、启动冒烟结果、峰值实测汇总、未关项全表。
2. **单列项报告法**：已知硬伤（如 B13 A6 门过渡单帧尖峰）单独成节报告：现状、实测值、影响面、处置建议，**不许混进总装结论的「通过」里稀释**；单列项的存在不自动否决上线，但必须由主窗口转 Thomas 知情。
3. **上线动作**：主窗口发令 → 推 town-release（整批一次推送）→ 等服务器拉取（约 2 分钟轮询）→ 逐字读 healthz 至 `town-preview <完整 SHA>` 与推送 SHA 一致 → 回报 Thomas「已生效」；任何一步对不上，报「未生效」并保留回滚点，不许报喜不报忧。
4. **上线后**：首访冒烟（真页面打开一次）、回滚点记录在案（上一版 SHA），出事按回滚点退。

## 附：本纲的修订

本纲由主窗口维护。施工中发现新坑（新的失败模式、新的绕过手法），当批补进本纲并注明日期与出处；旧条目与新裁定冲突时，以 Thomas 最新裁定为准，并把冲突登记进当轮矛盾排查。
