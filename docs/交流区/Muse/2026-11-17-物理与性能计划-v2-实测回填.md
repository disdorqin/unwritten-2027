# 物理与性能计划（Muse 负责：计划与性能）

日期：2026-11-17。分工（Thomas 21:49 定）：GPT 主线施工，**Muse 负责计划与优化性能**——本文件是物理玩法的实施计划与全镇性能的总账，后续每轮 A4 验收按本文件的预算与清单核对。

## 一、物理路线裁决：定向物理，不上全量引擎
结论先行：在现有碰撞数据（floors/ramps/colliders + blocked 层）上做**定向物理**，不引入 Rapier 全量接管。理由：
1. 小镇的碰撞世界已经是一套验证过的自定义数据（349 航点钟楼、三条路线、多轮仿真背书）；全量引擎等于把这套数据双写一份并重新验一遍，回归风险与工期都不划算（旧 `src/` 用 Rapier 是另一套运行时，与现页无关）。
2. 我们需要的物理只有三件：玩家跳跃（竖直速度+重力+落地支撑）、雪球弹道（抛物线+命中判定）、过河浮力/阻力（速度修正）。三件都是**解析式或小步积分**，不需要刚体求解器。
3. 真需要刚体的那天（可推道具、倒塌结构）再议引擎，接口按"物理步"预留。

## 二、不卡的四条纪律（借 MC 的模拟封顶思想）
1. **固定步长 + 与渲染解耦**：物理 60 Hz 固定步，渲染帧间插值；物理永远不许按渲染帧率放大步数（掉帧时物理最多补 2 步，多的时间丢弃——宁可慢动作一瞬，不可螺旋死亡）。
2. **空间格索引**：全部碰撞查询先过 64 m 空间格（与地形分块同格），只查所在格+邻格。**原型实测（ea3548b 真实场景，CPU 中位）**：雪球 64 并发——全扫 4.000 ms/步（帧预算 24.7%，不可上线）vs 格索引 1.181 ms/步（7.7%，达标）；32 并发格索引 0.585 ms；两策略命中数逐档相同（295/595/1208），格索引零漏检。结论：格索引是准入线，不是可选项。
3. **对象池 + 并发上限**：雪球对象池（建议上限 64 枚并发），超限回收最老的一枚；NPC 物理只做简化的定点/巡游，不做全刚体。
4. **物理预算线**：验收线 = 64 球并发压测下物理步 ≤1.2 ms（约帧预算 8%，含 1 名玩家步进；原型实测 1.181 ms 达标，常态 32 并发仅 0.585 ms）。玩家单步实测 60–94 µs，成本在既有 viewer 的 supportAt/obstructed 全扫而非新物理本身。

## 三、行为参数（初版，供 GPT 施工与 Muse 验收）
- 跳跃：跳高约 1.25 m（越 1.1 m 栏杆留余量），滞空手感靠重力 22 m/s² 量级调；无摔伤；跳跃中水平控制保留 80%。**参数必须按仿真标定**：原型实测离散积分会吃掉约 0.06 m——公式初速 7.416 只跳出 1.189 m，标定初速 7.74 实测 1.297 m。
- **前置数据修复（阻塞项）**：现四层 blocked 是纯 2D 无高度——栅栏类障碍无论跳多高都过不去。落地"跳过栏杆"前，必须给地面障碍加高度通道或把栅栏迁入 collider 层；此项不完成，跳跃验收第 1 条（指定栏杆可越）无法成立。
- 过河：涉水深度 <0.6 m 速度 ×0.55；更深进入游泳（贴水面、速度 ×0.45、可跳出水上岸衔接步高容差）。
- 雪球：初速 18–26 m/s 可蓄力，抛物线受重力 9.8–15 m/s²（取偏游戏感的值），命中判定半径按目标 AABB+0.15 m；命中反馈见打雪仗规格（迸溅+顿挫+计数，无伤害）。
