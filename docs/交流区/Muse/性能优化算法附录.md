# 性能优化算法附录（P4 执行与验收依据）

版本：2026-11-17，Muse 三路调研汇总（WebGL 前沿 / 体素算法 / 移动端保帧），原始调研报告存验收方工作区。
适用：`docs/任务书-性能玩法与世界扩展.md` 的 P4。手段取舍以本附录为准；与任务书冲突时先在本附录框架内解决，解决不了走交流区。

## 硬约束（重申）
- **画面与交互不许降级**：不收减面、删物件、关效果。只许剔除（看不见的不画）、批处理（换提交方式）、LOD 交叉淡入、动态分辨率（只动内部分辨率）、烘焙（把逐帧成本挪到构建期）。
- 预算线：中端手机 ≥30 FPS / PC ≥60 FPS；draw calls ≤300；可见三角形 ≤150 万；首屏可玩 ≤5 s（4G）。基线对照：性能基线报告（现图 ea3548b，另行交付）。

## 第一梯队（P4 主体，按序执行）

### 1. 批绘制总开关：BatchedMesh / InstancedMesh 按街区分块
- 静态几何按材质合并；重复构件 InstancedMesh；**不同几何、同材质的程序化构件用 BatchedMesh**（内部即 multi-draw，且内置逐实例剔除，绕开 InstancedMesh 整批一个包围球剔不掉的陷阱）——本项目建筑正是 BatchedMesh 的主场。
- 量级锚点：万级道具场景逐 Mesh 9,555 calls / 26 ms → InstancedMesh 21 calls / 2.2 ms → BatchedMesh 2 calls。这是达标 ≤300 的前提，其他优化都建立在它之上。
- 验收核法：四定点机位 draw calls 对照基线，须达预算；场景构成抽查无逐构件 Mesh 残留（地标动态部件除外，须注明）。

### 2. 全场烘焙光照 + 逐顶点 AO
- 现 22 个动态光源（Lambert 逐片元算光）→ 构建期把静态光写进顶点/面色，片元成本与光源数脱钩；动态光只留个位数**玩法光**（舞台、烟花、仪式点亮）。
- 雪夜是定妆场景、光源全静止，是全烘焙的理想情形；方块风用逐面定值与风格自洽。
- Voxelize 侧已自带这套（源码证实：光照 BFS 洪泛逐体素存储、网格化时烘进顶点），程序建筑侧照抄即可。
- 验收核法：运行时动态光源清点 ≤ 个位数（附清单）；四定点画面与烘焙前对照无可见退化。

### 3. 剔除组合：雾 + portal + 街区距离（PVS/软件剔除按数据决定）
- 雾剔除先行（全场最便宜，雪夜雾色与背景一致，天然掩护）；室内外 portal 简化版（相机在室内或入口阈值内才开室内组）成本极低、收益大头。
- 街区级距离剔除与 A3 的懒加载联动。PVS 预计算可见集、软件盒遮挡剔除（公开实测：街道视角视锥内 399 栋可剔 249 栋/62%，桌面 CPU 0.7 ms/帧）列为**数据驱动的第二步**：基线与第一梯队落地后，若街道机位仍不达标再上；手机 CPU 成本未证实，须目标机实测，可隔帧执行。
- 注意：过山车高空俯瞰视角下遮挡收益趋零，须与视角高度联动开关。
- 验收核法：街道机位可见建筑数/三角形对照；室内机位室外组关闭可查；高空机位无错杀（PVS 保守过估计原则：宁可多画）。

### 4. DPR 上限 + 动态分辨率缩放（DRS）
- 像素比硬上限 2，填充重的雪夜场景建议 1.5 起步（片段量随 DPR 平方：3→1.5 只剩 1/4）。
- DRS 在档位上限之下连续调节：帧时间窗口统计（45 帧 p75）、降快升慢、留 10–15% 余量、升档封顶——专门吸收手机热降频的时钟漂移（静态档治不了"十分钟后卡"）。
- 这是唯一"内容一个不少"兜底帧率下限的手段，与已定版的"流畅优先 + 自动降档"正合。
- 验收核法：持续运行 10 分钟的帧率曲线（不许后半程跌破预算）；DRS 升降无可见跳变（分辨率变化率受限）。

### 5. 透明 overdraw 治理（移动端头号隐形杀手）
- TBDR 的隐藏面消除只救不透明物体，透明层逐层真着色。实测锚点：某 Mali 场景可见透明水面占整帧 17.2 ms 中的 3.8 ms，而删被遮挡三角形只省 0.3 ms——要砍的是"看得见的透明层"。
- 本项目的高危组合正是**全屏降雪粒子 + 每盏灯的光晕精灵**。治理：雪改 GPU 粒子并按"全屏等效覆盖层数"定预算；光晕定额（远处不挂）；**移动档不用软粒子**（深度拷贝会强制 tile flush）；镂空不用 discard。
- 验收核法：Spector.js 帧捕获 + 分辨率缩放对照，或自制 overdraw 计数着色器抽查四定点。

### 6. Shader 预热 + 流式加载纪律（专打 1% low）
- Web 上 shader 首次渲染才编译，单次卡顿可达数百毫秒（有未预热首绘冻结约 2.8 s 的案例）。预热四件套缺一不可：加载屏 `compile/compileAsync`（须绑实际 render target，否则编错变体）、运行时不翻 define/光源数/透明的变体纪律、纹理预上传、特效留隐藏实例保活。
- 按街区流式：进区预加载、出区显式 `dispose()`（Three.js 不自动释放 GPU 资源）；KTX2 让 2048² 贴图常驻从约 16 MB 降到约 4 MB（对程序化建筑收益有限，价值在图片纹理与未来 GLB 管线）。
- 验收核法：冷启动到首帧可玩时间；逐区走入时无 >100 ms 的编译卡顿（帧时间尖峰清点）。

## 第二梯队（随扩图在构建期做）
- **HLOD 街区代理**：远处街区合并简化成 1–2 个 draw call 的代理，屏幕空间误差切换 + 抖动交叉淡入（alphaHash 或注入式 discard）。Three.js 无现成方案，需自研管线（估 1–2 周）；本项目代理可由生成数据在构建期直接产出，雪夜+雾对差异的掩盖天然友好。**必须在新图上做，旧图做了随重构作废。**
- **three-mesh-bvh**：给盒子碰撞覆盖不到的复杂几何（塔楼楼梯、桥、冰雕）做射线/碰撞兜底（实测射线 16 ms → 0.03 ms 量级），不替换现有 floors/colliders 盒子体系。接入成本低（半天到两天）。

## 纪律类（长期遵守）
- JS：固定步长模拟 + 插值；零逐帧分配（对象池、复用 Vector）；NPC 寻路/资源解码放 Worker；NPC 的 AI 更新错峰分帧。
- 后期：DOF/SSR 不用，SSAO 慎用；雪夜氛围用发光材质 + 高阈值半分辨率选择性 bloom（片段量 −75%）+ 精灵光晕 + 烘焙光池替代。
- 碰撞：街区网格空间哈希，在扩容把碰撞盒推上万级之前做掉（体素侧碰撞是 O(1) 数组访问，无此问题）。

## Voxelize 侧结论（源码级证实）
- 引擎服务端 mesher 已内建 **greedy meshing**（性能标签 "mesh: greedy"）+ 每段 15 位面-面可见性 connectivity（协议注明用于 occlusion culling）+ 烘焙光照——体素侧不用另造轮子。
- 注意点：合并率靠**调色板纪律**（1/16 米细构件会打碎合并，精修构件要控制）；draw call 随 renderRadius 平方涨，扩图后先核这项；开阔地遮挡收益有限。
- 体素网格化谱系锚点：8×8×8 实心块 naive 3,072 面 → culled 384 → greedy 6。

## 明确不做（及理由）
- **WebGPU 迁移**：WebGPURenderer 官方仍标 experimental 且不支持 onBeforeCompile/ShaderMaterial；12-31 前不迁，只留后路（新代码少新增自定义 shader 注入）。社区流传的"2–10 倍"对本类场景未证实。
- **Transvoxel**：解的是平滑密度场的缝，方块世界不适用；对应物是裙边/边界对齐 + 两级 LOD + 切换迟滞。
- **GPU occlusion query 首选**：结果异步晚 1–2 帧、物体须先被渲染才有数据、调用时机受限——只可用于藏贵重细节组，不开关主几何。
- **减面/删物件/关效果**：违反硬约束，不讨论。

汇总：Muse。执行中遇到与本附录冲突的现实约束，走交流区，不要自行降级画面或交互。
