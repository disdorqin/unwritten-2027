# 物理原型基准：跳跃 + 雪球投掷（基线 ea3548b 真实场景数据）

日期：2026-11-17。执行：Muse（子任务）。问题：给小镇加物理（跳跃/雪球）怎样才不卡——用实测数字回答。
原型代码（脚手架，非游戏源码）：`voxel-tavern/physics-proto-entry.ts`（主基准）、`voxel-tavern/physics-vault-diag.ts`（翻越诊断）。esbuild 打包后在 Node 24 离线运行，未访问 GitHub。

## 方法
- **场景**：与 A4 复验同一套组装（terrain + 全部建筑 + scenery/districts/streetscape/forest 四层 blocked）：**829 floors / 3 ramps / 1,893 colliders**，投掷物碰撞集 = floors+colliders+ramps 共 **2,725 个 AABB**（ramps 以其 AABB 近似，全图仅 3 条，已注记）。地图 448×384 m。
- **玩家物理**：逐行复用 viewer 的 `supportAt`/`obstructed`/`tryMove`/天花板检查语义；跳跃 = 竖直速度 + 重力 **g=22 m/s²**（注意：viewer 自身的坠落重力是 16.5，本原型按规格取 22），水平沿用 `tryMove`，落地用 `supportAt`。公式初速 v0=√(2·22·1.25)=**7.416 m/s**。
- **雪球**：对象池，半隐式欧拉 60 Hz 积分；碰撞 = 线段-AABB（slab 法）取最早命中 + 地形 `heightAt`（段终点+中点采样）。两策略同积分同判定，只差候选集：(a) 朴素全量 2,725 个全扫；(b) 64 m 空间格索引（7×6 格），只查雪球所在格+8 邻格（邮票去重）。发射参数由固定种子 RNG 在全图随机（初速 12–28 m/s、仰角 15–50°、寿命 8 s），死亡即重生保持并发数恒定；每档先 120 步预热 + 一轮弃置的满量预热。
- **计时口径**：全部头条数字用**进程 CPU 时间**（`process.cpuUsage`），每档跑 3 次取中位。原因：本机为共享 VM，墙钟在三轮运行间摆动 2–4 倍（第 2 轮墙钟中位为第 1/3 轮的 2–4 倍，同轮内 CPU 时间与第 1 轮低负载墙钟吻合良好）；CPU 时间只计实际上 CPU 的时间，可比性已由三轮交叉验证。

## 行为验证
| 项 | 结果 |
| --- | --- |
| 跳跃顶点（公式 v0=7.416） | 广场平地实测 **+1.189 m**、滞空 **40 步（0.667 s）**。理论顶点 1.25 m——60 Hz 半隐式欧拉系统性吃掉约 v0·dt/2≈0.06 m，**公式值在离散仿真里必打折，跳高参数必须在仿真内标定** |
| 跳跃顶点（标定 v0=7.74） | 实测 **+1.297 m**、滞空 42 步（0.70 s）。对 1.1 m 栏杆留约 0.20 m 余量，建议按此量级取值 |
| 翻越真实栏杆 | **未证成（如实记录）**。全图扫出 97 个"栏杆形"collider（0.9–1.35 m 高、薄、有底座面），但布景守卫（两侧 2.6 m 内须有栏杆底同高可站面）只放行 2 次尝试、且是同一处——钟楼楼梯旁的栏杆，其背后是墙体/楼梯实体，轨迹显示玩家在栏前被实体几何正确挡住（非跳高不足）。结论：真实场景里"两侧开阔的独立栏杆"在 collider 层里极少，机制层（空中 feet 高于栏顶后 `obstructed()` 放行）由同一套 viewer 函数保证，但端到端翻越未在真实几何上演示成 |
| **跳栏杆的真障碍（重要发现）** | scenery/districts/forest/streetscape 四层 blocked 是**纯 2D（只有 x,n，无高度）**，`walkable()` 在地面与空中一视同仁——**凡由这四层拦住的栅栏/篱笆，无论跳多高都过不去**。只有建筑 collider 层的栏杆是高度感知的。GPT 落地"跳过栏杆"前，必须给地面障碍加高度通道、或把栅栏迁进 collider 层，否则跳跃只在建筑区有效 |
| 雪球命中假人靶 | **命中**。投手在酒馆门前 [159,219]（地面 15.88，出手高 17.48），靶为广场 [223,190] 处 0.6×0.6×1.7 m AABB（y 12–13.7），水平距离 **70.3 m**。扫描（初速 30–50 m/s × 仰角 26–54°）首个命中组合：**初速 38.0 m/s、仰角 41°，飞行 147 步（2.45 s），弹道最高 y=31.40**（相对出手点 +13.9 m，理论 14.1 m，吻合）。命中经复核为全程最早命中（无建筑先挡）——弹道积分与命中判定在真实场景数据上成立 |

## 结论
1. **不卡的答案 = 空间格策略**。64 枚雪球并发（已是一场大型多人雪仗的量）+ 1 名玩家 = **1.27 ms/帧 ≈ 7.7%**，稳进 10% 物理预算线；常态 32 枚只有 4.1%。朴素全扫在 64 枚时吃掉 24.7% 帧预算，与渲染叠加后在中端手机上必卡，只在 ≤16 枚（6.5%）时勉强可用——**不要上线全扫**。
2. **并发上限建议：64 枚**（对象池定长、无每帧分配）。再往上先换 32 m 格再测，不要直接放开。
3. **玩家物理不是瓶颈**：60–93 µs/步 ≈ 帧预算的 0.4–0.6%/人。按线性外推（注：外推值，非实测）16 名玩家约 1.0–1.5 ms，仍可接受；其成本本质是既有 viewer 移动判定本身的成本，不是新物理引入的。
4. **固定步长解耦成立**：物理按 60 Hz 固定步推进、渲染插值，单步成本确定且远低于帧预算，不会出现追赶螺旋；本基准即按此结构测得。
5. **落地前必须处理的不是性能、是语义**：① 跳高按仿真标定（v0≈7.74 → 1.30 m），不要用公式值（实测只有 1.19 m，越 1.1 m 栏杆余量仅 9 cm）；② 四层 2D blocked 无高度，栅栏类障碍跳不过去——先给障碍加高度通道或迁入 collider 层，"跳过栏杆"才全镇有效；③ 端到端翻越栏杆未在真实几何上证成（唯一可布景的候选是钟楼楼梯栏杆，背后有实体），建议 GPT 落地时在广场/集市摆一处标准栏杆做验收点，Muse 按本原型的轨迹法复验。

数字均为实测（CPU 时间中位）；外推与未测项已逐处标注。未改游戏源码，未推送 GitHub。
