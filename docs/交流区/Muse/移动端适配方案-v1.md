## 一、外部调研结论（每条带来源）

### 1. 方向与全屏：网页锁不了 iPhone 的横屏，这是平台事实，不是努力问题
- `screen.orientation.lock()` 按 W3C 规范**必须先进入全屏**才允许调用，且需要用户手势触发；退出全屏自动解锁（MDN《ScreenOrientation.lock()》；多份 2026 指南一致）。
- 支持面：Chrome Android / Samsung Internet / Firefox Android 支持；**Safari iOS 至今（iOS 26.x）从未支持 orientation.lock**（caniuse 数据，见 forestrygames 2026-09 核查文）；iPhone Safari 的 Fullscreen API 也只是部分支持——iPhone 上元素全屏不可用（仅 iPad/桌面 Safari 完整），所以 iOS 连「全屏→锁横屏」这条链都走不通。
- 结论：**横屏只能「引导」不能「强制」**。通行做法 = 渐进增强（Android 尝试全屏+锁定）+ 竖屏旋转提示浮层 + 竖屏布局本身可用，三件套缺一不可。微信内置浏览器同理不支持强制横屏，行业通行解法就是提示横屏/提示在浏览器打开（亿屿 VR 全景漫游故障排查文）。

### 2. 安全区：`env(safe-area-inset-*)` 没有 `viewport-fit=cover` 就是一串 0
- 带刘海/灵动岛的机型上，`safe-area-inset-*` **只有在 viewport meta 写了 `viewport-fit=cover` 时才返回非零值**；不写时浏览器把页面 letterbox 在安全区内、所有 inset 恒为 0，CSS 写得再对也不生效（MDN 及多份实测文一致，见 kodiq《What is the safe area》、harshal-ladhe 教程）。横屏时刘海转到左右两侧，left/right inset 才是关键值。
- `dvh/svh/lvh` 动态视口单位 Safari iOS 15.4+ 全支持，是 100vh 问题的正解（mironsoft《CSS dvh, svh, lvh》系统文）。

### 3. iOS Safari 缩放怪癖：meta 锁缩放无效，正解是 `touch-action`
- iOS 10 起 Safari **故意忽略** `user-scalable=no` / `maximum-scale=1`（无障碍政策，WCAG 1.4.4），写了也白写（多份 2026 指南一致，含一份真实游戏项目的 iOS 兼容风险登记 big-break/docs/ios-compat.md，其头号风险就是双击缩放陷阱）。
- 正解：给可点元素加 `touch-action: manipulation`——关掉双击缩放、保留捏合缩放与无障碍（Andy Bell 2026-09 文，MDN 口径一致）；游戏画布用 `touch-action: none`。
- 另一条：iOS 对字号 <16px 的 input/select/textarea 在聚焦时自动放大页面；表单字号 ≥16px 可免。

### 4. 音频解锁：AudioContext 必须在手势回调内同步 resume
- 移动浏览器里 AudioContext 出生即 suspended，必须在 click/tap 的**同步回调内** `resume()` 并启动声源；隔了 await/setTimeout 就不再算手势、解锁失败（Chrome 开发者文档口径，Playgama 2026 汇总；iOS 尤甚，社区共识是 touchstart+touchend 双保险）。

### 5. Pointer Lock 在移动端不存在
- Pointer Lock 只存在于桌面浏览器；**iOS/iPadOS 任何版本、Chrome Android、Samsung Internet 均不支持**（WebKit bug 272168；testmuai 兼容性汇总）。移动端第一人称视角的唯一正解是 Pointer Events 触控拖动/摇杆——本项目已有（见 §二正面项），桌面锁定问题归指针锁定诊断管（§5 分工）。

### 6. DPR 与发热：封顶只是第一步，还要有帧时驱动的自适应降档
- 通行封顶 1.5–2（本项目已封 1.5，偏保守、没问题）。但移动 GPU 持续渲染 5–10 分钟后热降频，开始 60fps 的场景会掉到 20–30fps；成熟做法是**滚动帧时监控**：帧时持续超标就阶梯降 DPR（如 1.5→1.25→1），回暖再升回去（three.js 性能实践多份一致：intelligentgraphicandcode、wodh.io 生产指南、Pneumata 项目 performance.md 的 Adaptive DPR 实录）。

### 7. 微信内置浏览器
- 安卓微信 = X5 内核：WebGL 支持偶有黑屏个案（降复杂度可缓解）；iOS 微信 = WKWebView。不支持强制横屏、不支持 Pointer Lock、音频禁自动播放；Fullscreen API 需手势触发且支持度参差。行业通行兜底：检测到微信环境时给一条「点右上角 ··· → 在浏览器打开，体验完整」的提示条，不与平台硬刚（亿屿排查文、H5 微端通行做法）。

### 8. 小屏 HUD 收纳的通行模式
- 游戏 HUD 在小屏上的共识模式：**默认最小化（只留模式/菜单把手）→ 点按展开 → 点画布或数秒无操作自动收起/淡出**；情境提示走短暂 toast 而非常驻文本块；常驻信息只留一行状态。桌面 MMO/网页 3D 游戏与移动 H5 游戏皆同此理。本项目的 `#town-activity-status`（底部居中 toast、pointer-events:none、空即隐藏）已经是这个模式，可作全镇统一通道。

### 问题清单（按严重度排序）

**M-01viewport 缺 `viewport-fit=cover`，全部安全区代码失效**
- 现象：刘海/灵动岛机型横屏时，左侧摇杆、右侧跳跃键/雪球控件可能被刘海或手势条压住；竖屏底部控件与 home 指示条重叠风险。
- 证据：`town-blockout.html` 第 5 行 meta 只有 `width=device-width,initial-scale=1`；style.css 至少 10 处 `env(safe-area-inset-*)`（第 34、140、171、198、206、229–230 行等）。按调研 §2，无 cover 时 inset 恒为 0，这些代码全是死代码。
- 影响：所有全面屏手机（=现在几乎全部），横屏尤甚（刘海在侧面，正对摇杆/按钮区）。

**M-02没有任何横屏策略：无全屏入口、无方向锁定尝试、无竖屏旋转提示**
- 现象：Thomas 说的「横屏转不过来」——用户竖屏拿着手机进镇，画面是窄长条，没人告诉他横过来；横过来之后浏览器工具栏还占着上下，画布被动 resize。
- 证据：全仓 grep `requestFullscreen` / `screen.orientation` / `orientationchange` **零命中**；html 无任何旋转提示元素。
- 影响：第一人称在竖屏下横向视野极窄（见 M-06），不知情的用户直接判定「手机版不行」。

**M-03左上控制面板在手机上占屏且横屏高度溢出（副本基线）**
- 现象：面板常驻左上，内含标题+4 个模式按钮+前往下拉+取景按钮+帮助文本+坐标+预演+取景+2 个进度按钮。实测估算高度 ≈400px（小屏媒体查询后 ≈370px），**手机横屏视口高仅 360–430px，面板直接顶满甚至溢出屏幕**，且无 max-height、无内部滚动、无折叠（副本内）；竖屏时宽 304px 占 390px 屏宽的近八成。帮助文本 `#help` 是整段说明文字，常驻占位——正是 Thomas 说的「文本框挡视角」。
- 证据：style.css 第 8–9 行 `.panel` 无 max-height；唯一相关规则是 `@media (max-width: 580px) and (pointer: coarse)` 的尺寸微调（第 240–249 行），只缩字号内边距，不收内容。
- 影响：手机全程游玩被一块面板压着；横屏时面板与右侧雪球控件、底部摇杆三面夹击，中间没剩多少画面。
- 备注：GPT 的 town-panel 折叠（`2cea7b3`）是否已缓解此项，须在当前头核对（§5）——若它只做了桌面折叠且默认展开，手机问题依旧。

**M-04缩放手势未防：双击缩放 + 下拉聚焦缩放**
- 现象：连点面板按钮/互动键可能触发 iOS 双击缩放，画面跳掉回不来；点「前往」下拉（13px 字）iOS 聚焦时自动放大页面。
- 证据：style.css 中 `button, select` 字号 13px（第 11 行）、无 `touch-action` 规则（仅画布与摇杆/跳跃键有）；html meta 未写缩放锁（写了 iOS 也不认，见调研 §3，所以正解在 CSS）。
- 影响：iOS 全量；操作越急越容易触发，正是打雪仗/连点互动时。

**M-05画布尺寸双口径：CSS 100dvh 与 renderer 内联 px 不一致**
- 现象：iOS 工具栏伸缩、旋转设备时，`window.resize` 频繁触发，画布 CSS 高（100dvh）与 drawing buffer（innerWidth/innerHeight 内联 px）短暂不一致，画面拉伸/跳动；旋转瞬间尤甚。
- 证据：viewer.ts 第 82–84 行 init 用 innerWidth/innerHeight；第 1197–1203 行 resize 处理只听 `resize`、用 innerWidth/innerHeight `setSize`；全仓未用 `visualViewport`。
- 影响：iOS Safari + 安卓 Chrome 旋转/工具栏动画期间的观感抖动；属「奇奇怪怪的问题」的一类来源。

**M-06竖屏横向视野被裁：FOV 只锁纵向**
- 现象：相机纵向 FOV 固定 58°（viewer.ts 第 80 行），竖屏宽高比 ~0.46 时横向 FOV 只剩约 30°，像透过门缝看镇——这也是「竖屏玩不了」的物理原因之一（与 M-02 的提示互为表里）。
- 证据：`new PerspectiveCamera(58, innerWidth/innerHeight,...)`，resize 只更新 aspect 不动 fov。
- 影响：所有竖屏游玩者。通行解法：按宽高比反推纵向 FOV、保横向 FOV 恒定（宽屏封顶）。

**M-07DPR 固定档、无帧时自适应：发热后帧率一路下滑无救济**
- 现象：手机玩 5–10 分钟发热降频后帧率掉下去，再不回来；当前 DPR 1.5 是写死的（viewer.ts 第 82 行），没有任何降档/回升逻辑。
- 证据：全仓无帧时统计、无 setPixelRatio 二次调用。
- 影响：中低端安卓与老 iPhone 的持续游玩体验；与多人负载方案的帧时线（p95 ≤33.3ms）正好共用一套监控，别各写一份。

**M-08微信环境零处理**
- 现象：朋友从微信点链接进来（最可能的分享路径）时：不能全屏、不能锁横屏、X5 个案黑屏——页面不给任何提示，用户只觉得「坏了」。
- 证据：全仓无 UA/环境检测、无微信提示条。
- 影响：微信内打开的全部用户。

**M-09音频解锁链不完整**
- 现象：钟声/烟花音效在 iOS 上可能首触无声。
- 证据：`festival.ts` 第 112–119 行 `tryEnableAudio()` 有手势内 resume 的意识（正面）；但 `tower-chime.ts` 的 `playTowerChime(context,...)` 由外部传入 AudioContext，其创建/resume 是否在手势同步回调内，未在本副本核清。
- 影响：iOS 上仪式音效可靠性（跨年夜是重头戏，值得单独验）。

**M-10其余小项**
- 无 `theme-color` meta，浏览器顶栏颜色与夜空不搭（小事，一行）。
- 对话卡 `#place-card`/`#museum-card` 小屏已近全宽且有 max-height+内部滚动（正面），但卡内按钮最小高度只在内容区保证了 40px，关闭键等未统一到 44px 触控标准（Apple HIG 口径）。
- 竖屏时 `#festival-status` 大字（clamp 28–63px）横向可能溢出——已 `white-space: nowrap` + 居中，短文案无碍，长文案需验。

## 三、施工方案（分级）

### 必修（挡路的，先做）

**B-1 补 viewport-fit 与主题色**（对应 M-01）
- 改法：`town-blockout.html` 第 5 行改为 `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`，另加 `<meta name="theme-color" content="#121e35">`。**不加** user-scalable/maximum-scale（iOS 不认且伤无障碍，调研 §3）。
- 文件：town-blockout.html 一行。
- 连带核查：cover 生效后页面真的画到刘海底下，逐个验 style.css 已用 env() 的控件（摇杆、跳跃键、雪球控件、状态条、导览条、地图键）位置正确；`.panel` 左上在横屏刘海侧需补 `left: max(16px, env(safe-area-inset-left))`（小屏规则同理）。
- 验收：真全面屏 iPhone + 安卓各一台，横屏进第一人称：摇杆完整可见不压刘海、跳跃键不压手势条；竖屏底部控件不与 home 条重叠。

**B-2 横屏策略三件套**（对应 M-02；策略全文见 §四）
- 改法：
1. **旋转提示浮层**：新增 `#rotate-hint` DOM（纯叠层，零 GL）：`body.touch-play` 且竖屏且处于第一人称/俯瞰游玩态时显示「把手机横过来，雪镇会更好玩 ↻」+ 一个「知道了」关闭（关后本会话不再弹）；横过来自动消失。用 CSS `@media (orientation: portrait)` + 一个 body 类控制，不写 JS 方向监听也行，显隐逻辑挂在现有模式切换点上。
2. **渐进增强全屏+锁向**：第一人称按钮的点击处理里，触控设备上尝试 `document.documentElement.requestFullscreen()` 后 `screen.orientation.lock('landscape')`，全程 try/catch 静默失败（iOS/微信自动落空、无副作用）；退出第一人称或 Esc 时 `screen.orientation.unlock()`。必须在手势同步链内调用（调研 §1/§4 同理）。
3. **竖屏兜底可用**：靠 B-3 收纳 + A-1 的 FOV 补偿保证竖屏也能玩，提示只是引导不是门禁。
- 文件：town-blockout.html（加浮层节点）、style.css（浮层样式+竖屏媒体查询）、viewer.ts（第一人称进入/退出处挂全屏尝试，约 10 行）。
- 验收：安卓 Chrome 点「第一人称」→ 自动全屏横屏（或至少全屏）；iPhone Safari 竖屏进镇 → 出现旋转提示、横过来提示消失且画面正常；微信内打开 → 提示出现、不报错。

**B-3 面板收纳统一：三态 + 默认最小**（对应 M-03；策略全文见 §五）
- 改法（与 town-panel 的关系先核对后施工，见 §5）：
- 手机（pointer: coarse）：面板默认**收起态**——只留一条标题栏（标题 + 展开把手），其余（模式按钮组、前往、取景、预演、进度）全在展开层里；展开层 `max-height: calc(100dvh - 24px); overflow-y: auto` 兜底任何屏高。
- `#help` 整段说明**移出面板**：改为首次进入各模式时走 `#town-activity-status` 同款 toast 通道播一次（现有 announceActivity 机制），不再常驻。
- 展开后点画布、或 6 秒无操作 → 自动回收起态（游戏 HUD 通行模式，调研 §8）。
- 桌面端保持 town-panel 已定的折叠行为与 localStorage 记忆；手机端的收起态不写 localStorage（每次进镇默认收起，防「上次展开着这次挡脸」）。
- 文件：style.css（coarse 媒体查询段）、town-panel.ts（若核对后由它承载）或 viewer.ts + town-blockout.html（若自建把手节点）。
- 验收：任意手机横屏进镇，首屏左上只有一条细栏、画面无大块遮挡；点开能用全部功能；点画布自动收起；横屏 360px 高机型展开层可滚到底、无溢出死区。

**B-4 缩放手势防御**（对应 M-04）
- 改法：style.css 全局加 `button, select, #world-action, #touch-jump { touch-action: manipulation;}`（画布/摇杆已有 none 不动）；「前往」select 与信件 textarea 等表单字号在 coarse 下提到 16px（或全局表单 16px，桌面不受影响的做法是只在 coarse 媒体查询里改）。
- 文件：style.css 两处。
- 验收：iPhone 上连点互动键 10 下页面不缩放；点「前往」下拉页面不放大；安卓同验连点。

### 应修

**A-1 竖屏 FOV 补偿**（对应 M-06）
- 改法：resize 与初始化时按 aspect 反推：目标横向 FOV 恒定约 66°（桌面 58° 纵向在 16:9 下的横向等效），`vfov = min(58, 2*atan(tan(hfov/2)/aspect))` 的反向公式——竖屏时放大纵向 FOV 保横向视野，宽屏回到 58°。touch-look.ts 内部自带一份写死的 `verticalFov = 58°`（第 1 行）用于点按转向换算，**必须改成读同一来源**，否则点按转向角度错位。
- 文件：viewer.ts（相机段+resize 段）、touch-look.ts（FOV 注入）。
- 验收：竖屏站在广场，左右可见范围与横屏截图对照基本一致；竖屏点按画面边缘转向落点准。

**A-2 画布尺寸口径统一**（对应 M-05）
- 改法：resize 处理合并 `resize` + `visualViewport.resize`（若可用）双通道、rAF 节流合并同帧多次触发；尺寸来源统一用 `document.documentElement.clientWidth/clientHeight` 或 visualViewport 尺寸，与 CSS 的 dvh 口径对齐；旋转时允许一帧过渡不闪。
- 文件：viewer.ts resize 段（第 1197–1203 行附近）。
- 验收：iPhone Safari 反复旋转 5 次 + 上下滑动工具栏伸缩，画面无拉伸残留、无黑边；安卓 Chrome 同验。

**A-3 帧时自适应 DPR**（对应 M-07）
- 改法：帧循环里加滚动帧时统计（与多人负载方案共用同一监控实现）：帧时 p95 连续 2 秒 >26ms → DPR 阶梯降（1.5→1.25→1.1→1），连续 10 秒 <17ms 才回升一档（迟滞防抖）。只动 setPixelRatio，不动其他画质（沿用「不降内容」纪律）。
- 文件：viewer.ts 帧循环段。
- 验收：中端安卓真机连续游玩 10 分钟，记录帧时曲线：降档发生且帧率回稳；桌面端不触发降档。

**A-4 微信提示条**（对应 M-08）
- 改法：检测 UA 含 `MicroMessenger` 时，在加载完成页/面板收起条上方出一条可关闭提示：「微信里打开功能受限，点右上角 ··· 选择『在浏览器打开』体验完整雪镇」；仅提示、不拦截游玩。
- 文件：viewer.ts（检测+复用 toast/横幅通道）或 town-blockout.html + style.css 小横幅。
- 验收：微信内打开链接能看到提示且能关；在浏览器打开无此条。

**A-5 音频解锁核对与补齐**（对应 M-09）
- 改法：核对 tower-chime 的 AudioContext 创建点：确保与 festival 一样在用户手势同步链内创建+resume；统一收口到一个 `ensureAudio()`（手势内调用），钟声、烟花、仪式音效共用。
- 文件：tower-chime.ts 调用方、festival.ts、town-ceremony.ts 接线处。
- 验收：iPhone Safari 全新打开页面（无任何点击历史）→ 走到钟楼第一次敲钟有声；跨年预演第一次点即有声。

## 四、横屏策略（定稿口径）

**一句话：推荐横屏但不硬锁——安卓走「进第一人称自动全屏+尝试锁横屏」的渐进增强，iOS/微信锁不了就用旋转提示浮层引导，竖屏靠 FOV 补偿与面板收纳保证同样能玩。**

理由：iOS Safari 与微信在平台层就不给锁向能力（调研 §1、§7），任何「强制横屏」的努力在这两家都是白费；把劲用在「引导到位 + 竖屏兜底」上，覆盖面才是 100%。

## 五、文本框收纳策略（定稿口径）

统一到**一个收纳机制**，不要每个框各 invent 一套：

| 框 | 现状 | 策略 |
|---|---|---|
| 左上控制面板 `.panel` | 常驻全展开（副本） | 三态：桌面沿用 town-panel 折叠（展开/收起，localStorage 记忆）；**手机默认收起只剩标题条**，点把手展开、点画布或 6 秒无操作自动收起，不记 localStorage |
| 帮助文本 `#help` | 面板内常驻整段 | **移出面板**：模式切换/首次触发时走 `#town-activity-status` toast 通道播报一次，常驻位只留面板展开层里的一行短提示 |
| 坐标 `#position` | 手机 ≤580 已隐藏 | 保持；展开层里可见即可 |
| 加载状态 `#load-status` | 触控已隐藏 | 保持 |
| 情境状态 `#town-activity-status` | 已是 toast 模式 | 保持，作为全镇统一的临时文案通道（新提示一律走它，不新开常驻框） |
| 对话卡 place-card / museum-card | 模态 dialog、小屏近全宽 | 保持模态（这是「读字场景」，全屏化是对的）；只补 O-1 触控尺寸 |
| 仪式横幅/倒数 ceremony-* | 已是限时 DOM 叠层 | 保持 |

与 town-panel 的衔接（**施工前必做的一步核对**）：在集成分支当前头读 town-panel.ts/css，确认三点——①它是否有 `(pointer: coarse)` 分支；②折叠态在手机上默认是展开还是收起；③它管的是否只有 `.panel` 一个框。核对结果决定 B-3 是「给 town-panel 加手机分支」还是「另起收纳层」：**优先前者**（一个机制管全端），只有它结构上做不到时才后者，并把理由写回交流区。

## 六、与桌面指针锁定诊断的分工边界

- 桌面「其他电脑视角不跟准心」问题归 **desktop-look.ts + 指针锁定诊断**管辖，本方案不碰 `desktop-look.ts` 与 Pointer Lock 逻辑。
- 截至本稿，`~/workspace/unwritten-ceremony/reports/` 里**尚无 pointer-lock-diagnosis.md**（只有 ceremony-client.md），该诊断未落盘——**待衔接**：等它落盘后互相引用即可，两边无文件交叠（对方：desktop-look.ts/viewer 桌面段；本方案：style.css/town-blockout.html/触控段），唯一汇合点是「进入第一人称的引导 UI」：桌面的「点击锁定视角」提示与移动端的全屏/横屏引导挂在同一个进入动作上，文案位不要各占一块屏，施工时以先落盘一方的 DOM 结构为准、另一方复用。
- 移动端视角（touch-look）已自成体系且质量合格，不在对方诊断范围内；对方若要验「无指针锁定环境回退」，回退实现就是本方案的触控路径，不要再写第三套。
