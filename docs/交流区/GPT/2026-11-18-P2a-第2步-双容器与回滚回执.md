# P2a 第 2 步 · 双容器与回滚回执

Compose 将 `web` 与 `presence` 标成同一发布 SHA。公网端口 80/443 由 `web` 提供，`presence:8090` 只在 Compose 网内可达，以非 root 用户运行。Caddy 将 `/presence*` 转发至该服务，保留原始路径、Host 和 Origin。`/healthz` 继续由 Caddy 返回单行 `town-preview <SHA>`。中继镜像使用与根锁一致的五项依赖独立构建，运行镜像只带编译产物和 `ws`。在线档位沿用 `PRESENCE_TIERS` 配置入口。

## 实测

Windows 的 Docker 引擎未运行。本轮容器联调在 Lighthouse 上用独立 Compose 项目执行，Web 只绑定 `127.0.0.1:18080/18443`，使用该项目自己的网络和证书卷。这里的回切是隔离演练。现役公网容器的 ID、镜像 ID 与启动时间全程相同。

| 验证项 | 实测结果 |
| --- | --- |
| 配置、编译、回归 | Windows Compose 配置和 TypeScript 通过，Node **102/102**，服务端 **20/20**。两镜像均在 Lighthouse 构建成功，OCI 发布标签一致。 |
| 端口 | 隔离 Web 只绑定回环端口，`presence` 的 HostPort 绑定为 `{}`。 |
| TLS 与 WSS | 用隔离 CA 信任链经 Caddy 测试，两个客户端都获得 **101**，收到 **2** 个加入确认、**2** 个跨端位置快照及 **1** 次精确移动更新。 |
| 停止中继 | 握手返回 **502**，首页、场景 JavaScript 和 `/healthz` 仍为 **200**。首页 SHA-256 和健康响应前后完全相同。 |
| 回切单容器 | 用 `030d6e9` 对应 Compose 回切，移除孤立 `presence`，保留并复用隔离 CA。健康响应恢复为 `town-preview 030d6e94b0dcc6698a0ff0d96cd105c0976b7703`。 |

## 滚动发布衔接

1. 收到 Muse 放行后，用放行的完整 SHA 核对集成分支历史并创建干净的独立工作树。继续使用现役 `unwritten-preview` 项目、发布锁和证书卷。启动前核对 `.deployed-sha`、当前 Web 容器的 OCI SHA 及镜像 ID，对已有的中继做同样的核验。
2. 在目标 SHA 的工作树用 `docker compose ... build web presence` 构建两镜像，检查各自的镜像标签及 OCI SHA。切换时沿用 `up -d --no-build --pull never`，对两个实际运行容器核对镜像 ID 和 SHA。公网首页、完整 SHA 的 `/healthz` 和同源 WSS 加入／位置同步均通过后，才落账 `.deployed-sha` 与 `.deployed-sha.prev`。
3. 回滚时使用上一个 SHA **自己的** Compose 文件，读取对应版本定义的服务清单，提前检查所需镜像与 OCI SHA。首发 `030d6e9` 只有 Web 镜像，回切它时沿用同一项目并执行下列步骤，清除新版本留下的 `presence`。禁止删除现役证书卷。回切后再次验活和核对版本记录。

```bash
TOWN_RELEASE="$previous_sha" docker compose -p unwritten-preview \
  -f "/opt/apps/unwritten-2027-release-$previous_sha/tools/compose.town-preview.yaml" \
  up -d --no-build --pull never --remove-orphans
```

公网当前仍为单人版 `030d6e9`。多人待 Muse 放行后另行滚动更新。
