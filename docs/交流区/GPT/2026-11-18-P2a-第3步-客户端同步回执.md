# P2a 第 3 步 · 客户端同步

- 第一人称进镇后连接同源 `/presence`。出站按 10 Hz 采样脚位、朝向，走动转为静止时发一次终止状态以消除预测速度，随后静止不再发状态。玩家名保存在现有浏览器本地配置时可读取，默认分配临时游客名。进出提示使用现有 `announceActivity`。
- 远端按 120 ms 延迟插值、最多预测 250 ms。明显位置跳变清理旧轨迹，序号回绕和重复数据有专项覆盖。连接失败、超时或断线清空远端状态，无弹窗，保留本地游玩。
- 最多绘制 48 个访客。复用 NPC 的 22 个体素模型，每帧至多一批实例。昵称放入 48 项 DOM 池，超过 40 米、在视锥外或镜头后时隐藏。昵称只按文本渲染。NPC 始终是本地逻辑。
- 保持预览 Dockerfile 的原有构建上下文。客户端和服务端各自的薄协议实现用线格式互操作测试锁定偏移和坐标语义。

## 本机验证

- Windows 本机两组独立 Chrome 上下文用临时同源代理接真实 Node presence。最终优化版双方互见昵称和方块人，真实 W 键行走约 4.31 米，远端首次收敛观测约差 0.18 米。远端看到了起跳高度变化 0.354 米。离开 80 米后回收，返回广场恢复。停点观测不计作轨迹 RMS，未把高度变化计作跳跃时延。
- 停止临时 Node 服务后远端清空，另一端仍能实际行走约 2.31 米及切换视角。浏览器没有未捕获页面异常。此处使用本机服务进程，Docker 停容器回归留给后续步骤。
- 广场单人 136 次绘制、1,130,448 个三角。带一名可见访客 137 次、1,130,712 个三角。俯瞰前后都是 277 次、1,474,016 个三角。组件单独验证 48 同屏仍是一次绘制、12,672 个三角，清空后额外绘制为零。通过四向朝向、41 米标签剔除、视锥裁剪和纯文本昵称验证。
- Windows i9-14900HX、Chrome 146，48 人全可见移动，预热 100 帧后测 300 个真实 RAF。实例矩阵与参考实现最大误差 4.73×10⁻⁷。模型与名牌组件 CPU 均值由 0.143 降至 **0.060–0.061 ms**，P95 由 0.255 降至 **0.090–0.120 ms**。两轮后测单帧最大值分别为 **0.525 ms**、**0.185 ms**，第二轮 300/300 帧低于 0.3 ms。完整同步链路的每帧上限仍需第四步核验。
- 客户端严格 TypeScript、`town-preview` 生产构建、Node 102/102、服务端 20/20，新增三项客户端专项覆盖线格式、静止终止样本、短弧插值、丢帧预测上限与瞬移。
