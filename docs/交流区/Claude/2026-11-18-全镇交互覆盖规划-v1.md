# 全镇交互覆盖规划 v1

- 日期：2026-11-17
- 作者：Muse（规划与性能口）

## 1. 原则

### 1.1 覆盖率目标

- **每个地标 / 功能区至少 1 个真交互**：真交互 = 玩家主动触发、有明确反馈、有状态或结果（计数、留存、成绩、作品、关系变化，任一即可）。只能看、只能路过的建筑视为缺口。
- **街道、桥、河等过渡空间至少 1 个轻交互**：轻交互 = 一次按键 / 点按即完成、反馈即时、不要求停留（翻看、拾取、敲击、留印类）。
- 覆盖以第 2 节覆盖表逐行打勾为准，全表无缺口才算达成；新增建筑 / 区域落地时必须同步登记一行，无交互方案不得交付。

### 1.2 性能纪律（硬约束，先于玩法）

全镇现行总预算不变：任一标准视角绘制调用 ≤300、可见三角形 ≤150 万；D6 尚未达标的中距（463）与缩放峰值（554）优先占用整改空间，**新增交互不得吃掉 D6 争回来的余量**。每项新交互必须复用共享系统，不许自带一套：

- **统一交互框架**：邻近提示 + E 键（移动端点按）触发，提示 UI、触发距离、冷却逻辑全镇一套；新交互只注册「触发点 + 回调」。
- **对象池粒子**：雪花、蒸汽、涟漪、炊烟、烟花共用既有粒子池与固定容量，禁止每交互新建粒子系统；雪仗已定的池上限（雪球 ≤64）为先例。
- **DOM 覆盖层**：输入、留言、相框、望远镜遮罩、火候条等界面一律走 DOM，**零 WebGL 绘制调用**（受击反馈设计已验证此路线）。
- **实例化道具**：许愿牌、灯笼、柴垛、冰雕等可增殖物件一律 InstancedMesh / 单批次，数量增长不涨 draws。
- **不新增常开光源**：发光效果一律自发光贴图 / 烘焙 / emissive；确需动态光的提案直接否决或改 DOM/贴图方案。
- **贴图进图集**：牌面、招牌、明信片、时刻表等小贴图并入共享图集，禁止一交互一张独立纹理。

单项预算：

- 该交互在其**本地视角** draws 增量 **≤ +5**（实测，见第 4 节）；
- 玩家**远离时零全局成本**：交互物件与逻辑随地块懒加载 / 卸载，卸载后 draws 与内存回基线；
- 状态存 **localStorage**；事件形状统一预留多人同步字段（如 `{type, actor, target, payload, t}`），单机先行、多人阶段不返工。

### 1.3 与既有系统的关系

新交互优先挂到已落地系统上长出来（集邮、调酒、雪仗、NPC 对话、护照），不另起炉灶；具体衔接见第 3 节。

## 3. 与既有系统的衔接

### 3.1 护照 / 戳册

- **核心规则不动**：现有 7 戳 + 7 灯集齐兑换跨年纪念卡的判定与存档结构保持不变，新交互一律不塞进核心 7 戳，避免破坏已验收的集齐逻辑与老存档。
- **新增「扩展收集页」**：车票盖章（火车站）、冰钓渔获图鉴、滑冰/雪橇个人最佳、冰雕与灯笼作品登记、堆雪人留名等走扩展页收集，与核心戳册同存一份 localStorage、分开计数。
- 每个新交互立项时必须声明它在护照里的位置：核心（原则上不再新增）/ 扩展页 / 不入册，三选一写进验收单。

### 3.2 NPC 熟络

- 熟络分层台词（初见/再访/常客）已在语料侧备好，新交互是它的**主要解锁通道**：给 NPC 送饮品（酒馆，按口味偏好）、讨价还价成功（集市摊主）、温泉同泡彩蛋（随机 NPC）、点灯/演出等公共活动的共同参与，都应记熟络+并触发对应层级台词。
- 熟络计数沿用 NPC 系统现有存档，不新建第二套关系数据；新交互只发事件（见 1.2 的事件形状），由 NPC 系统决定台词与态度变化。
- 内容纪律不变：NPC 相关文案只用已记录事实与已备语料，拿不准的走当面 deflection，不虚构。

### 3.3 雪花币（D7，未拍板）

- **状态：待 Thomas 确认，不阻塞其余任何一项。**
- 本表全部提案按**零货币可玩**设计：试吃免费、灯笼材料免费、冰雕免费，荣誉/成绩/作品即奖励。
- 仅在数据层预留钩子（价格位、奖励位字段，默认 0），D7 一旦拍板再统一接线，不逐项返工；拍板前任何提案不得以「等货币系统」为由延期。

## 4. 验收口径

- **打勾制**：覆盖表逐项验收，逐项打勾；未过不打勾，缺陷续 D 编号登记，修完复验才勾。
- 每项落地必须过 A4 式验收，以下六条全过才算成立：
  1. **可触发**：PC（E 键/长按）与移动端（点按）双通道实测可达，触发点不被几何遮挡（吸取邮局窗户活动点的教训，新触发点做全盘可站立扫描）；
  2. **反馈成立**：视觉/音效/状态变化至少其一可被玩家明确感知，动画无跳变；
  3. **本地视角 draws 增量实测** ≤ +5（GL-hook 计数，与落地前同机位对比）；
  4. **远离零成本抽查**：离开该地块后 draws、纹理、缓冲区计数回基线，无常驻更新循环；
  5. **存档留存**：涉及留存的项（种花、灯笼、留言、许愿牌、成绩类）刷新后复查仍在；
  6. **回归不破**：旧路线回归（酒馆/博物馆/钟楼三线）与全镇构建、回归测试通过。
- 性能总账复核：每批交互落地后重测四标准视角（广场/纪念馆/冰湖/酒馆室内），总预算超标即冻结新交互、先还 D6 的账。

## 附：成本风险提示（作者自评，易被低估的 3 项）

1. **春灯工坊·做灯笼（表中记 高，仍可能低估）**：难点不在生成一只灯笼，而在「玩家自选挂点 + 持久留存」——挂点合法性校验（不能挂进几何里）、多只灯笼的实例批次管理、存档结构与老存档迁移，三件都是隐形工作量。
2. **灯塔·旋转光束（表中记 中，实则偏高）**：光束是全镇最大的透明体之一，移动端透明 overdraw 正是既有性能结论点名的头号风险；与雾、雪粒子叠加时的填充率需专项实测，中档预算可能兜不住，必要时改「贴图光锥+DOM 辉光」的降级方案。
3. **桥上打水漂（表中记 中，实则偏高）**：多次弹跳的水面物理（入水角/速度衰减/跳数判定）不是现有雪球抛物线的简单复用，且「未冻河段」需先实测确认位置与季节状态（冰湖已冻、河段结冰情况待核），判定做糙了手感立刻露馅。
