# 给主窗口：服务器与客户端内存占用实测（Thomas 2026-11-19 点名）

背景：Thomas 问现行游戏在服务器上大概占多少内存。服务器为朋友腾讯云 Lighthouse（2 核 / 2 GB 内存 / 50 GB SSD / 4 Mbps / 月流量 300 GB)。Muse 侧 SSH 被平台出口拦截、读不到线上计数；Muse 已在本地同构建实测一个基线值：`node dist/server/server/index.js` 空载 RSS ≈ 87 MB（healthz 正常）。请你用现行测试台把负载口径补齐，回执给实测值。

## 要测的四项

1. **服务端空载**：现行集成线构建的 server 进程启动后稳定态 RSS（与 Muse 的 ≈87 MB 对版；口径不同须注明）。
2. **服务端带载**：用仓内 bots 工具（`npm run bots` 或现行等价入口）模拟 8 / 20 / 30 个玩家在线，分别记录稳定态 RSS 与每增一名玩家的边际增量；注明 bots 的行为模式（静止/移动/语音有无），静止挂机与满场活动分开报。
3. **客户端**：Chromium 测试台全镇巡游一圈（广场→钟楼→集市→冰宫动线）时的 JS heap 与渲染进程内存峰值，注明机型与 DPR 口径（沿用 M6 回执的 Intel UHD / DPR1 台即可）。
4. **推算**：按 2 GB 上限给出结论——空载占比、30 人满载占比、离上限的余量；若某项异常吃内存，指出是哪一块（模型/音频/状态存储）。

## 纪律

- 数字必须实测，回执逐项给值与测法；测不到的写「未测」与原因，不许估算冒充实测。
- 本任务不改任何代码；若顺手能给 server 加一个自报 `process.memoryUsage()` 的只读小接口（如挂在既有状态口径下），可作为附带提案写进回执，先提案不实施。
- 回执带「本轮已读 Muse 新文件」行（常驻循环协议）。
