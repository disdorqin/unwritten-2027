# 技术文档 · 技术栈、建模方法与交互实现（2026-11-21，总控维护）

本文是全仓唯一的技术口径文档：用什么技术、模型怎么建、交互玩法怎么写代码。新入线者读完应能照着现有件的样子写新件。细节实现以文中点名的正典模块为准，照着抄结构，不要另 invent 框架。

## 一、技术栈

| 层 | 选型 | 说明 |
|----|------|------|
| 渲染/引擎 | **Voxelize + Three.js**（体素引擎） | 用户已认可体素酒馆的方块风格与基础结构，全镇沿用；不迁移、不换引擎 |
| 语言 | TypeScript（全仓） | 客户端、服务端、测试同语言 |
| 构建 | Vite | 镇版构建：`tools/voxel-tavern` 内 `npm run build -- --mode town-rehearsal`；类型检查 `npx tsc --noEmit` |
| 联机权威 | Node presence 服务（`src/presence/`，Docker 镜像） | 每空间域一个房间/端口（镇 8090、山 8091、西 8092、天空 8093、矿 8094）；同一程序多房间，玩家只在本域内同步 |
| 部署 | Caddy 反代＋pull-deploy | 总控推 `town-release` 分支，服务器每 2 分钟轮询拉取、按 SHA 建 worktree 部署，healthz 必须精确回读 `town-preview <SHA>` 否则自动回滚 |
| 测试 | node:test + tsx（328 个测试文件） | `node --import tsx --test tests/*.test.ts tests/server/*.test.ts`；场景级另有 `tools/verify-*.mjs` 浏览器验收脚本，一件一脚本 |
| 本地运行 | `node tools/run.mjs dev|check|build|start` | 避开 Windows npm shim 引号问题（仓库 AGENTS.md） |

## 二、世界怎么组织（代码落点）

- 世界本体在 `tools/voxel-tavern/town-blockout/`（444 个模块）：地形、建筑、场景、玩法客户端都在这里，一件一模块，文件名带线前缀（见《项目地图》前缀表）。
- 跨端共享规则在 `src/shared/`（44 件）：纯规则与数据（状态机、点位表、公式），客户端与服务端共用同一份，**规则只许有一份实现**。
- 服务端权威在 `src/presence/`：各域房间、缆车/仪轨等权威状态机的宿主与事件校验。**硬规矩：presence 内 import 只许引 `src/shared`（带 `.js` 扩展名）或本目录，禁止引 `tools/`**——镜像构建上下文只有 `src/`，引 tools 必挂（第十版部署卡死 35 分钟的教训，详见《项目文档-经验教训与协作规范》）。
- 接线层只有两个文件：`viewer.ts`（主查看器，挂载一切、管 currentAction）与 `town-presence.ts`（客户端联机层）。**单写者**，任何线只走增量补丁，不许整文件覆盖。

## 三、建模方法（模型是代码建的，不是文件堆的）

1. **体素拼装**：建筑与景物由代码用体素块/盒体逐件拼装（builder 模块导出构建函数，返回 THREE.Group 挂入场景）。逐块结构必须读得出来——纯色长方体粗模已被用户否决（仓库 AGENTS.md），构件数量不能代替视觉验收。
2. **像素纹理**：材质用程序生成的低分辨率像素纹理（canvas 生成，如 16×16），`NearestFilter` 强制。纹理要成片成理（层理、砖缝、木纹），**禁止逐像素哈希噪点**（斑点岩事故：单像素三色跳＋错用色值，实景读作「加载错误的模块」）。
3. **配色**：全镇一张色板（《风格打造规范-粘土工厂味》）：石灰 #8a8378／土黄 #a98a56／深褐 #5d4630／墨绿 #44503c／夜蓝 #2c3648／雪白 #e8ecf0／火光橙 #e08a3c／晶辉青 #7fd4c8／锈红 #8a4a34。色值各有归属（如夜蓝是天空/夜色，**不许拿去当岩石底色**），新件配色先查规范。
4. **地形三件套**：①基座 `terrain.ts`（冻结，不动）；②起伏 `terrain-undulations.ts`——解析函数叠加（多模正弦），统一掩码（道路/铁路/地块/湖岸 5 m 内归零、36 m 缓坡肩），新区域只许在此扩展参数，不许新开第二套；③坑体 `meteor-crater-surface.ts`——实测剖面生成的行走网格（B-01），坑内一切落点以它为坐标源，远景调色只改顶点色不动高度。
5. **先图后建**：标志性物件施工前必须有参考图入 `docs/参考图/`（crater 11 图、mountain 86 图），验收截图与参考图同角度对照。
6. **台账预算**：每包登记 draws/tris/灯数增量（实测，不许估），超基线的增量要用 carve-out 在台账测试里明示。密度靠实例化与合并，不靠堆 draw。
7. **七轮施工法**（GPT 侧常驻）：R1 主体建模→R2 补完→R3 修碰撞/穿模→R4 对图精修→R5 细节材料→R6 交互玩法→R7 验收合入。前三轮不许用接口/单测冒充建模完成。

## 四、交互玩法怎么写代码（四层模式，照正典抄）

任何多人交互按同一四层落地，缺层不算完成：

1. **规则层（src/shared）**：纯状态机＋点位/公式数据，无渲染、无网络。例：缆车修缮 `za36-cable-repair`（锈闸恰 9 敲、正缆重挂恰 3 环、配重 4 块任意序、非法输入 no-op）、冰晶宫仪轨 `ice-palace-rites`。先写规则层定向测试（恰数、边界、非法输入）。
2. **权威层（src/presence）**：宿主状态机、校验客户端事件（allowlist＋形状校验＋限流，受理才广播）、join 时下发全量快照帧（迟入房者同步当前态）。例：`cable-line-authority.ts`、`ice-palace-rite-authority.ts`。多人状态永远以权威层为准，客户端不许自判。
3. **活动层（town-blockout）**：场景内的交互点位用「活动」模式——点位表（spots）＋`step()` 驱动＋可选宿主接口注入。例：冰晶宫 `createIcePalaceLandmarkActivity(options)`，options 注入 rites/fragmentPickup 宿主；无宿主时点位诚实休眠，不许假装能玩。单人本地玩法（无多人状态）可省略权威层，但要在回执写明。
4. **接线层（viewer.ts）**：把活动挂进世界、把动作接进 `currentAction` 优先级链（E 键提示取当前情境的首选动作：乘降判定→宿主动作→坑区动作→通用动作，顺序在接线包里写明），阶段播报文案当场写定。接线是独立一步、独立成包，不许混在建模包里顺手改 viewer。

**单人/多人分界**：凡是「别人也要看见状态变化」的（修缮进度、仪轨、拾取、协作绞盘）必须走满四层；纯本地表现（看/听类）可只走活动层。协作类规则在规则层就要定死人数语义（例：绞盘乙案——单人 40 s、第二人稳绳 ×1.8、进度永不回退）。

**跨域**：玩家跨域靠转场「醒」（黑场＝切房间），域内坐标自洽；地面路线步行连通不设空气墙，跨域点只在设计口（山口守卫拦人是「人」拦、不是墙拦）。

## 五、验证口径（写完怎么算对）

- 快速构建口径（游戏侧常驻）：构建过、浏览器启动零报错、功能第一人称走一遍——三件齐才报完成；
- 交付质量门（批37）：代码＋定向测试＋昼夜第一人称截图（注机位坐标与朝向）；
- 涉 presence 的包另跑镜像编译模拟（总控切版门，配方在《项目文档》教训篇）；
- 本地无头浏览器的帧率不作性能结论，性能只认真机 live 对测。
